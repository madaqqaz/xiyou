## ① 当前游戏内容（代码事实）

> 硬规则：每条数值/机制必须带 `file:line` 或 BalanceDB 键；无证据者移入 §⑥。

### 1.1 核心循环
入口 → 决策 → 反馈 → 结算，均以 `s.equips`（数组）为持有容器：

1. **获取**：战斗/精英/Boss/坊市/事件多渠道。随机掉落走 `NDX.rollEquips(n, state, preferSlot)`（`data_equip_core.js:503`）；精英装备二选一走 `NDX.rollSetEquips`（`:665`）；掉落落地在 `game_loot.js:_grantAdvDrops`（`js/game/game_loot.js:12`）。
2. **入库去重**：`NDX.Game.prototype.grantEquip`（`js/game/game_equip.js:2`）——法宝按 `treasureId` 唯一（`:10`），非法宝按 `id` 唯一（`:14`），高阶替代低阶兜底 `isSupersededByHigherTier`（`:19`，真源 `data_equip_core.js:486`）。
3. **决策（择优上阵）**：`NDX.activeEquipsFor(ctx)`（`equipment_part3.js:1204`）按类别分格取件——身体四槽各 1（`:1209`）、器胚 1（`:1214`）、灵宠按 `petSlotCapFor`（`:1215`）、法宝只纳祭出式（`:1219`）；手动 `active=true` 锁定优先、`manualOff` 弃权，缺省按 `_equipScore`（`:1170`）自动取前 N。切换入口 `toggleEquipActive`（`:1236`）满位时自动撤下评分最低非锁定件（`:1255`）。
4. **结算**：生效件属性并入战斗，真源在 `combat_part1.js computeStats`（见耦合矩阵 §二）；面板侧 `NDX.AttrCalc.computePlayerStats`（`attr_calc.js:282`）与 `applyPostProcessing`（`:404`）为唯一活跃聚合入口。
5. **反馈**：获得时 `bus.emit('loot')`（`game_equip.js:73`）、图鉴记录 `NDX.CODEX.record`（`:60`）、新手指引 `triggerTeach`（`:35`）。

### 1.5 边界与异常
- **rng 可注入**：`rollEquips`/`rollSetEquips` 全部走 `NDX.runRandom()`（`data_equip_core.js:581/586/594/707`），受整局播种流约束，可复现。⚠ 例外：`game_loot.js:26` 的朝代 eliteDrop 追加倍率判定用裸 `Math.random()`（见 §1.7）。
- **择优幂等 / 空数组语义**：`companionLineupOf` 显式区分「未指定(null→自动取前 N)」与「主动清空(空数组→不补满)」（`equipment_part3.js:213-217`）。
- **去重三重**：`rollEquips` 排除已拥有 + `shownEquips` 曾展示 + 同 `treasureId` 阶段（`:504/512/517`）；池空时放宽"曾展示"约束但仍排 eventOnly（`:589-597`）。
- **跨英雄隔离**：`ownerOk` + `setBelongsToOtherHero`（`:515/553`，真源 `:643`）杜绝非主角英雄套流出。
- **存档零迁移**：成长字段缺失按 0（`data_equip_growth.js:21`）；槽位归一化不改数据侧 106 条 `'treasure'` 字面量（`equipment_part3.js:406`）。
- **自动合成死循环防护**：`_autoCraft` 有 `guard++ < 100` 上限（`game_equip.js:155`），并要求 `availableRecipes` 与 `chooseCraft` 前置校验严格一致（`data_equip_core.js:426-434`）。
- **clamp**：红判定 `setTier>=3`（`isRedEquip:387`），减伤/成长封顶 `Math.min(spec.cap,...)`（`data_equip_growth.js:55`）。

### 1.7 已知债务与死区
> ⚠ 以下均为**实测代码债务**，本审计只登记不改码。

1. **【实锤·重复定义】`SLOT_CAP` 等槽位块整段定义两次**：`NDX.SLOT_CAP`（`equipment_part3.js:168`）与第二次（`:272`）内容**完全相同**，其间 `achvSlotBonus`（`:173` 与 `:277`）、`companionSlotCap`（`:184`/`:288`）、`_companionScore`（`:190`/`:294`）、`companionPoolOf`（`:195`/`:299`）、`companionLineupOf`（`:208`/`:312`）、`toggleCompanion`（`:230`/`:334`）、`dynastySealSlot`（`:248`/`:352`）、`sealSlotCap`（`:252`/`:356`）**逐函数重复**（约 L166–257 与 L270–361 两段）。后写覆盖前写，运行期等价，但属维护地雷（改一处漏一处）。对应耦合矩阵 §1.3 已登记项，本审计**复核确认仍存在**。
2. **【双处声明·潜在分叉】随从池 cap**：`SLOT_CAP.companion=4`（`equipment_part3.js:168`）与 `data_negotiate.js:20` `followerCap:4` 各写一份，当前同为 4，无常量联动，未来单改即口径分叉。
3. **【数据坍缩 bug·高危】`RECIPES` 约 90 条配方材料重复键静默丢失**：多条成长配方写作 `materials: { '玄铁': 2, '玄铁': 1 }`（如 `equipment_part2.js:15`、`:34-39`、`:44-49`、`:105`–`:247` 区间，实测 `'([^']+)': \d+, '\1'` 命中 **90 处**、其中 `'玄铁':N,'玄铁'` **87 处**）。JS 对象字面量重复键后者覆盖前者 ⇒ 实际坍缩为 `玄铁:1`，**期望的多次累加（×3）静默降为 ×1**，合成成本远低于设计意图。消费端 `recipeReqFor:397`/`availableRecipes:446` 均以 `Object.keys(req)` 读取，无法察觉重复。P0 数值债务。
4. **【死代码】`attr_calc.js` 大多为遗留内联**：文件头标记「仅 `applyPostProcessing` 活跃，其余为旧内联死代码」（`attr_calc.js:2`）；全仓 `AttrCalc.` 仅 1 处外部消费（`game_meta.js:46` 调 `applyPostProcessing`），`calcFinalAttrs/calcEquipmentBonus/calcSealBonus/traceAttrSource` 等**零外部调用方**，`computePlayerStats` 亦仅在函数群内自引。真正生效的装备聚合是 `combat_part1 computeStats`。
5. **【忽略字段】`e.red`**：`isRedEquip` 明确「`e.red` 为无赋值来源的残影字段，一律忽略，以 `setTier>=3` 为准」（`equipment_part3.js:383-389`）。
6. **【rng 不一致】** `game_loot.js:26` elite 追加掉落用 `Math.random()` 而非 `runRandom()`，破坏该掉落的 seed 可复现性（与装备主链 §1.5 相悖）。
7. **【悬空显示名】** `toggleEquipActive` 满位提示与 `_equipKind` 注释仍称第 5 栏「器胚」（`equipment_part3.js:1186/1213`），但用户 2026-09-26 已拍板改回「特殊装备」（`:400-401`，`EQUIP_SLOT_LABEL.special='特殊装备' :434`）——注释/文案与显示真源不同步。
