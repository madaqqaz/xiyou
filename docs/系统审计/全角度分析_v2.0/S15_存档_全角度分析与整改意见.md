### 2.11（补充）长线留存 · 经济 · 内容量视角

1. **长线留存**：本系统是**唯一承载「跨周目」承诺的通道**（`xynj_cycle` + 觉醒印记 CAP 9 / PCT 3% + 碑塔 200 条 + 剑冢 3 节点）。`JOB_LEGACY_CAP=9 × PCT=0.03 ⇒ 满槽 ×1.27`（`data_trials.js:488-489,714,730`）在数值上给了 27% 的成长，但**继承数据若因 `clearAll` 残留 / 迁移失效而丢，跨周目承诺即落空**｜**P0**
2. **经济吞吐**：局末入账链路 `recordRunEnd` 串 8 类落盘，其中 ASH（劫灰 `:106`）、RUBBING（拓印 `:102`）、MONUMENT（碑塔 `:104`）**直接是跨周目经济源**；三者全部在 `try/catch` 静默分支内 ⇒ **一次异常 = 玩家损失当世全部跨周目收益**｜证据：`data_save.js:100-119` 五个独立 try/catch｜**P1**
3. **内容量缺口**：无实质关联。存档不改变内容量，但**会决定玩家是否愿意投入内容量**——丢档风险越高，长线内容投入的回报率越低。
4. **三端存储 API 差异与降级矩阵**（本视角的技术底账，也是「Platform 回拢」要保住的契约）：

| 后端 | 契约实现 | 迭代能力 (`length`/`key`) | 降级行为 | 配额 | 清缓存后果 |
|---|---|---|---|---|---|
| **H5 浏览器**（`platform/browser.js:10-32` `mkStorage`） | 包 `localStorage`，另提供 `get/set` 双形态 | ✅ 透传（try/catch 兜 `0`/`null`） | `:36-43` `localStorage` 不存在时退内存 Map | ~5 MB | 清站点数据 ⇒ **全丢** |
| **TapTap 买断版**（`platform/taptap.js:26-38`） | 包 `localStore`，另提供 `get/set` | ✅ 透传（同 browser 写法） | 同 browser | 视 WebView | 清数据 ⇒ **全丢 + 买断凭证丢**（R10） |
| **Platform fallback**（`platform/index.js:33-54` 内建对象） | 内建于 `index.js` | ✅ 自实现（`order` 数组维护顺序） | 无——**这是最后一级** | 内存，刷新即空 | 刷新 ⇒ **全丢** |
| **`storage.js` tier-3 内存兜底**（`storage.js:124-132`） | **每次调用新建对象** | ❌ **硬编码 `length:0` / `key:()=>null`** | 见 R14 ⇒ `clearAll` 前缀扫描空转 | 内存 | 刷新 ⇒ 全丢 |
| **`save_system.js` tier-3 单例**（`save_system.js:28-38`） | `window.__ndxSaveStoreFallback` 单例 | ✅ 自实现（`order` 数组） | 无 | 内存，刷新即空 | 刷新 ⇒ 全丢 |

> **契约一致性判定**：前三级（browser / taptap / index fallback）**均完整实现 `getItem/setItem/removeItem/length/key`** ✅，满足 `save_system.js:19` 注释声明的「localStorage 兼容 API」契约——**这是 V9.63 回拢能成立的技术前提，且落地正确**。唯一契约缺口在 `storage.js:130-131` 的**自造后端**：它声称自己是后端，却声明 `length:0`、且 `_storeKeys()` 只能返回 `[]`，导致**依赖后端迭代能力的 `clearAll` 前缀扫描在该后端下整体空转**（R14）。
> **降级链的真实形状**：`NDX.Platform.storage` → `localStorage` → `platform/index.js` 内建对象；而 `js/storage.js` 与 `js/save_system.js` 各自还有一条**平行的** `localStorage` → 内存 兜底。⇒ **实际是 3 条并行降级链，不是一条**。两链的最后一环都"刷新即空"，但**只有 `save_system.js` 那一环是单例**，`storage.js` 那环每次新建 ⇒ 同一会话内 `storage` 层的内存档在 `clearAll` 前后可能指向不同对象。

5. **渐增型存档是唯一需要盯的容量项**：实测碑塔满 200 条 = 35 KB（`data_save.js:163` 硬上限），是三项中最大的单项；`_audit_save_capacity.js` 的上界估算是 **153.2 KB / 5 MB = 2.99%**。`xynj_monuments` 若将来上调上限，容量增速是**线性**的（每条约 178 bytes）——按 200 条不变，配额面永无风险；若放宽到 1000 条约 175 KB，仍安全。**结论：容量不是本系统的风险项**。
6. **跨周目经济的"最后一公里"缺失**：`recordRunEnd` 落盘了 ASH（`data_save.js:106`）、RUBBING（`:102`）、MONUMENT（`:104`）三类跨周目经济源，但**落盘动作玩家不可见**（`try/catch` 静默）。玩家在第 3 周目拿到的 27% 觉醒加成（`data_trials.js:730` ×1.27）**没有任何界面告诉他"这是因为你前两世存下了 X 条碑塔"**——长线经济的因果链在玩家侧是断的。落点应是 UI 而非存档代码。
7. **与付费的耦合**：`privacy_policy.md:48` 声明"单机离线、无内购、无广告"。实现侧 `platform/taptap.js:47` 的 `BUYOUT_KEY='ndx_buyout_v1'` 是**买断**而非内购，与声明一致 ✅。但买断凭证与存档同后端（R10）意味着**付费状态本身处在存档风险敞口内**——这是本系统唯一涉及"钱"的存档面，建议优先于其他 P1 处理。

### 3.1 反证记录（对"存档可完整还原"与"Platform 已收口"的两组反证）

> - 连带：`migrateAll()` 对上述档调用仍返回 **0**，自愈路径同样为空转。

> **反证二 · 「Platform 是否已完成收口」**——寻找残留散落判定：
> - 正面（`_verify_storage_platform_bridge.js` 16 断言全绿）证明了 `js/storage.js` 单文件内零裸直连。
