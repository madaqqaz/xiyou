## 〇、执行摘要（TL;DR）

一句话：**S01 的病不在"内核不够强"，而在"内核能力与玩家可感知之间那三层管道漏了"。** 内核能逐回合换姿态、能吃 6 职特色、能让随从放群火；装配层不给、门禁看不见、UI 不让点。

- **真问题 1 · 装配层白名单截断 —— 多条已在 computeStats 算好的成长，走到战斗就归零。**
  实跑三向差集：`computeStats` 顶层输出 **23 键**，装配白名单 `_playerObj`（`game_combat_1.js:353-394`）透传 **24 键（含 4 个 coll 子键）**，交集之外还有 **6 个"有产出 ∧ 内核有读点 ∧ 未透传"** 字段：`finalDamage` / `engineTier` / `petPassive` / `petCombo` / `followerSkills` / `hp`；再加 `immuneDeath`、`hpDrainPct`（写在 `st`，`_playerObj` 不读）与 **`coll` 四键的宿主错配**（写入方 `attr_calc.js:522-530` / `game_meta.js:114-122` 都写 **st**，读取方 `_playerObj` 读 **s**）。
  同种子 A/B 实测代价（`.tmp/s01_wiring.cjs`，LCG 固定 seed=999）：终伤 `finalDamage=0.6` ⇒ 敌残血 **Δ−2949**；`petCombo=0.30` ⇒ **Δ−4781**；`engineTier{multi:2}` ⇒ **Δ−2894**；随从红孩儿 ⇒ **Δ−2550**；`coll` 四键 ⇒ **Δ−2637**。阳性对照（白名单内的 `armorPen/shieldPct/lifesteal/reflect`）全部生效 ⇒ **方法学自证，不是脚本失真**。

- **真问题 2 · 门禁全绿，因为它们手写复刻了同一个错误。**
  `_verify_final_damage.js:21/0` 的 `mkP(fd)`（`:113-119`）与 `_verify_stance_xinmo.js:10/0` 的 `player()`（`:47-52`）都是**手搓 player 字面量**，不是 `computeStats → _playerObj` 的产物。于是"21/0"与"实机 finalDamage 恒 0"同时成立 —— 而 `_verify_final_damage.js:7` 头部注释**自己就写着**"42 项门禁无一项调用 computeStats ⇒『全绿』与『一走就崩』同时成立"。修了 computeStats 盲区，却在装配层**重建**了同类盲区。`_verify_follower_fuse.js` 更彻底：全文**没有一次 `calcCombat`**，`:318` 甚至把"无新开战斗接线"当成通过条件。

- **真问题 3 · STANCE 三缺二：spec 的三根轴只落了一根，且落的那根"守"是零代价零收益。**
  spec §3 定义 `ATTACK = 气势×1.5 / 精气×0.7 / 心魔+K`、`GUARD = 气势×0.7 / 精气×1.5 / 心魔−K`。实况：
  - `STANCE_MUL`（`combat_part1.js:564`）**只有 `mom`，jingLi 系数从未落地** —— `battle_resource.js` 全文 341 行**零 stance 字样**，spec §7 接线点第 4 项（`battle_resource.js:197 gainJingLi` 乘系数）不存在。
  - **气势轴上 GUARD ≡ 中性**：（`gainMomentum`（`:569-571`）用 `Math.round(k×0.7)`，而 `k` 全仓只有 **1**（`:935` 命中）与 **2**（`:977` 绝境击杀）两个值 ⇒ `round(0.7)=1`、`round(1.4)=1` ⇒ 守姿态每回合增益被**压平为 +1**，与"根本没开姿态"的中性兜底**逐位完全相同**：`[1,2,2,3,3,4,4,4,3]` vs `[1,2,2,3,3,4,4,4,3]`（`.tmp/s01_stance.cjs` 实跑）。攻态则 `[2,4,5,5,5,5,5,5,4]`，**三势封顶从第 8 回合提前到第 3 回合**。⇒ spec §8 失败信号 A（"取舍假"）**不是风险，是已发生事实**。
  - **心魔侧反而过冲**：`_stanceXmNet += STANCE_XINMO[_stance]`（`:1277`）**每回合累加、无任何 CAP**，落账走 `gainXinmo(..., {cap:false})`（`game_combat_1.js:414-418`、`:593`）**绕过章封顶**（`game_event_3.js:834` 的 `CHAPTER_CAP` 只对 `n>0 && cap!==false` 生效）。实测 ±2×回合：Boss 8–20 回合 ⇒ **±16~±40**，已越 spec §5 承诺的 `XINMO_CAP ±25/单局`；100 回合拉锯局（内核硬上限 `MAX=100`，`:1076`）实测 **±200 = 承诺值的 8 倍**。

- **真问题 4 · 决策密度实测为 0：spec 要"每回合唯一决策"，实装是"整局一次、且默认沿用上局"。**
  内核**完全支持**逐回合（`opts.stanceSeq[round]`，`:1141`；喂 100 元交替数组实测逐回合生效 `[2,3,4,5,5,5,5,5,4]`）。但生产只传**一元数组**：`{ stanceSeq: [s.stance||'ATK'] }`（`game_combat_1.js:403`、`:580`）；UI 与后端双重锁死在"尚未结算任何回合"（`ui_panel_1.js:241`、`game_combat_1.js:571` 同一式子 `phase==='intro' || (phase==='wait' && roundIdx<=0)`，注释自称 **"Shape A"**）；而 `s.stance` 是**整局持久字段**（`game_event_1.js:76 stance:'ATK'`），不逐战重置 ⇒ 玩家切过一次之后，此后每一战都自动沿用，**再不会回来点它**。`roundsDetail` 的每回合对象里**没有 stance 字段**（`:1302-1343` 实读）⇒ 回放时无从显示"本拍攻/守"。

- **真问题 5 · 四轴资源互不相通，玩家看到的是"三套半血条"。**
  气势 `momentum`（0–5、三阶，**只活在预结算内核**）｜战意 `zhanYi`（8–15，**只活在手动脉** `game_core_3.js:235-249`）｜经力 `jingLi`（3–7，同上 `:254-258`）｜心魔（0–100，全局）。内核不认识战意/经力，`pending` 不认识气势 ⇒ STANCE 只能调制四轴中的一轴的一半（见问题 3）。同时 `data_battle_plan.js`（已加载 `index.html:326`，`:8-11` 契约要求"同一 (seed, plan, interventionList) 必须 100% 复现 roundsDetail、禁止读 `Math.random()`"）**全仓零外部消费者**，与内核 25 处裸随机直接冲突 —— 重放契约写了但没有执行者。

- **好消息**：表现层与"手感"已不再是短板（§⚠ ⑦）；钳制族（dr/eva/blk/mdef/sunder/finalDamage/lifesteal 七封顶 + 段和恒等不变量）**完备度高于全部竞品**（§4.3）。

### 4.3 本作的三项独占优势（不要妄自菲薄）

1. **钳制族完备度 > 全部竞品**：`dr≤0.60 / mdef≤0.50 / eva≤0.60 / blk≤0.50 / counter≤0.40 / sunder≤0.9 / pMdef≤0.85 / clampHp=baseHp×4 / FINAL_DMG_CAP=2 / LIFESTEAL_CAP=0.5` 十道闸（§1.4）。竞品普遍只有 2–3 道，且不外露。**这是"改一处即可全局收敛"的工程红利。**
2. **V9.39 逐乘区记账 + 段和恒等不变量**：每一分伤害都能回溯到"哪一段、哪个乘区、几毫秒飘字"，并有 `assert 段和 === deal` 锁死（`_verify_final_damage.js:143-144`）。竞品的伤害归因多是黑箱。
3. **预结算架构（一次算完 ≤100 回合，`roundsDetail` 供逐拍回放）**：天然支持"回放、快进、战斗小结、AI 决策标注（`ai.targetRule/pSpd/mSpd`）"，这是 DD/StS 都需要自建 state machine 才能做到的事。**也因此，"逐回合玩家决策"在本架构里是可行的**（§1.8 已实测逐拍换姿生效）——只要 UI 敢问。

### O3 ·（**P0**）给 GUARD 一根真收益：受击减伤 + 气势/经力双供给，并让 STANCE 调制 spec 承诺的第二根轴

  1. **消掉取整塌缩**：`gainMomentum` 改为**浮点累积 + 拍末取整**（`momentumF += k × mom; momentum = Math.floor(momentumF)`），使 `1×0.7=0.7` 真能低于 `1×1.0`。目标曲线：GUARD 第 9 回合 `momentumAfter` 从实测 **3 → 2**。

  3. **补 spec 的第二根轴**：`STANCE_JINGLI = { ATK: 0.7, GUARD: 1.5 }`（spec §5 原值），落点 `battle_resource.js:199 gainJingLi` 的 gain 上乘系数；同时 `gainZhanYi`（`:178-183`）对偶取 `ATK ×1.3 / GUARD ×0.7` ⇒ 打通"姿态 ↔ 战意/经力"，让四轴至少两轴联动（修§1.5 资源割裂）。

- **验收门禁**：T1/T2（O2）为硬门；另加 **T5 守端有效性举证**：同种子对同一 Boss 8–20 回合局，`GUARD` 的 `playerHpLeft` 高于 `ATK` **≥ 8%** 而 `rounds` 不多于 +30%；**T6 资源联动**：`pending.jingLi` 在 GUARD 下 9 回合累计 ≥ ATK 的 2.0×（1.5/0.7 的理论比）。

### 8.4 方法学反思：代码即真源的“实时性陷阱”

> 正文开篇必带“**基线声明**”，形式如：“本文 file:line 取证于 YYYY-MM-DD HH:mm；基准 = `file1.js` NNN 行 (mtime HH:mm) + `file2.js` MMM 行 (mtime HH:mm)”。代码一旦变动，行号不可靠但 **结论可重新映射**（如本 §8.2）。不内嵌基线声明的文档，一年后都是旧文档。
