## 〇、TL;DR

**现状**：双层门面 `NDX.storage`（注册表 + 版本注入 + 三级后端兜底）与 `NDX.SaveSystem`（类型化原语 + 键搬家 + 批量 API）叠在 `NDX.Platform.storage` 之上；断点 RUN 走 `autoSave→storage.save`，跨局 meta 走 `recordRunEnd` 8 类落盘，寄存匣/排行榜/碑塔各自持键。容量维度**健康**（实测 153.2 KB / 2.99%，无 base64、无图片音频入档）。

**五条真问题（全部实测，非推测）**：

1. **碑塔"越新越丢"**：`list.push(新)` 之后 `slice(0, 200)` 留的是**最旧** 200 条（`js/data_save.js:155-163`，同一 bug 在 `js/data_monument.js:35-43` 重复定义一份）⇒ 满 200 世后每一世新增碑塔写进去就被裁掉，而展示侧按 `ts` 降序（`js/ui/ui_misc_2.js:513`）⇒ 玩家永远看不到新世。
2. **版本迁移整链是"结构性安慰剂"**：`migrateAll()` 恒 0（更正 #3）；`SAVE_VER` 前跳时 `_migrate` 因缺 `MIGRATIONS[2]` **一步都不执行却盖章成新版本**（`js/storage.js:99-112`）；`SaveSystem` 侧另一套 `__v` 字段与 `_version` 互不可见（探针 C：同键 `_version=2 / __v=undefined`）；而 `save()` 走 `SaveSystem` 时**根本不写任何版本戳**（`js/save_system.js:165-173`，原始串实测 `{"good":5,"evil":3}`）。
3. **断点续玩"读后即删 + 零备份 + 零退出钩子"**：`restoreRun` 成功后立刻 `remove(KEYS.RUN)`（`js/game/game_rest.js:23`），恢复→下一个安全点之间若崩溃/杀进程 = 整世归零；全库 grep `_bak|backup|_prev` 无任何存档备份机制。竞品 Hades 在"每次回到冥殿"时**自动留下带时间戳的 .bak 供游戏内回滚**。
4. **三端只有两端可跑**：宪法 AGENTS.md:122/125 要求 `platform/wechat.js` + `wx.setStorageSync`，实测 `platform/` 内**无 wechat.js**（`platform/index.js:2` 自述"微信段已取消"，同文件 :5 又写"三个子实现…wechat.js"，5 行内自相矛盾）；`taptap.js:35` 的"TapTap 本地存储"**其实就是 webview `localStorage`**，未接任何 TapTap 原生/云存储 API；且当 `localStorage` 不存在时，`storage.js` 的 tier-3 兜底 **每次调用都 `var m = {}` 新建一个 Map**（`js/storage.js:124-132`）⇒ 写与读落在两个不同对象上，**持久化 100% 蒸发且全程不抛异常**。桥门禁的降级用例只测到 tier-2（`scripts/_verify_storage_platform_bridge.js:133-140`），tier-3 从未被断言可回读 ⇒ 门禁 16/0 绿灯掩盖了它。
5. **重置存档清不干净**：`nx_hero_unlock_v1` / `nx_clear_v1` 前缀漏（更正 #6）⇒ 玩家点「重置全部存档」后，**英雄永久解锁与通关记录、以及依赖它们的"逆道"抉择门全部残留**（`js/data_config.js:106-114` 的 `xynj_perfect_clear_v1` 虽前缀可清，但同样不在注册表）。

**竞品一句话**：Hades / StS / Rogue Legacy 的共同点不是"有云存档"，而是**把写档收敛到少数几个语义安全点 + 保留上一份可回滚副本**；本作有安全点概念（`autoSave` 两处）却没有副本概念。

**优先级**：P0 = O1（碑塔留存方向）/ O2（版本真源与零迁移告警）/ O3（断点双档回滚 + 退出补写）/ O4（tier-3 兜底单例）；P1 = O5（clearAll 收口）/ O6（落盘可观测）/ O7（断链大扫除）/ O8（裸调收编 + 门禁扩域）；P2 = O9（校验和自愈，明确不做对抗式加密）。

## 四、差距评估（适合 / 不适合 + 为什么）

| 竞品做法 | 适不适合本作 | 理由（结合三端约束） |
|---|---|---|
| A. 局末自动留 N 份带时间戳副本 + 游戏内回滚（Hades） | ✅ **适合，最高优先** | 本作已有清晰语义安全点（`recordRunEnd` 8 类落盘处、`settleReturn`/`_dieByLife`）；只需在写前 copy 旧值，零构建可用；成本主要在键数控制——只对**高价值可变键**（碑塔/剑冢/RUN/排行榜/业藏录）开副本即可，不必 31 键全覆盖 |
| B. 多存档槽（Hades 4 槽） | ❌ **不适合** | 本作 meta 是"唯一世界进度"（跨周目累计、排行榜、剑冢互引），多槽需要给 12 个未注册键全部加槽后缀，且 `nx_`/`ndx_`/`xynj_` 前缀体系会炸裂；三端配额与 UI 均不划算 |
| C. 每个房间都写、只保留最后位置（StS） | ⚠ **部分适合** | "每个安全点都写"的语义本作已具备（2 处），缺的是**写失败可感知**与**删档前先备份**。不建议改为节点级即时写：`snap` 是全 state 深拷贝（13.9 KB/次），高频写在小游戏 webview 上有卡顿风险 |
| D. 云存档同步 | ❌ **现阶段明确不适合** | `AGENTS.md:15` 把"无后端、无账号体系"列为非目标；且 StS/Hades 的一手教训是：云 + 本地双写会把"损坏"变成"跨设备互相覆盖"。若未来接 TapTap 云存档，**前置条件是 O2（版本真源）+ O9（校验和）先完成**，否则一次冲突即永久丢档 |

## 五、可实施优化设计

> 每条含：问题 → 目标值/结构 → 落点（owner `file:line`）→ 验收门禁 → 优先级 → 回归风险。

### O1【P0】碑塔/排行榜"留存方向"修正 + 重复定义合并

- **问题**：`data_save.js:155-163` 与 `data_monument.js:35-43` 双份同 bug —— `push(新)` 后 `slice(0,200)` 留旧；`data_rank.js:48-54` 双榜拼 40 再 `slice(0,20)` 丢空 imperfect 榜。
- **目标值/结构**：碑塔 = **保留最新 200 条**（`if (list.length > 200) list = list.slice(list.length - 200)`），`MONUMENT_MAX` 提为常量并写注释说明展示侧降序依赖；排行榜 = **每榜各 20**（`saveRank` 不再全量截断，改为按 `board` 分字段截断，落盘容量上界 40 条 ≈ 3.8 KB，远低于任何端阈值）。
- **落点**：`js/data_save.js:155-163`、`js/data_monument.js:9-43`（**删重，仅保留 `data_save.js` 一份**，或反之；同时核对 `index.html:292/293` 加载序）、`js/data_rank.js:20/48-55`。
- **验收门禁**：新建 scripts/_verify_save_retention.js（待落地） —— vm 沙箱写 210 世碑塔，断言 `len==200 && 含 M210 && 不含 M1`；提交 25 条通关记录（15 perfect + 10 imperfect），断言两榜均非空且各 ≤20；顶层重复函数定义扫描（同一 `NDX.xxx = function` 在 js/ 出现 ≥2 次即红）。
- **优先级**：P0（数据不可逆丢失，且玩家可感知：新世碑永远不出现）。
- **回归风险**：低。仅改裁剪方向；`ui_misc_2.js:513/554` 与 `ui_changan.js:157-159` 是降序/计数读取，行为只增不减。**已存盘的旧玩家**碑塔里存的是"最早 200 世"，修后新增会正常追加、旧条目不再被裁 → 无需迁移。

### O2【P0】版本真源统一 + "零迁移即告警"（根治升版丢档）

- **问题**：`migrateAll` 恒 0（先盖章后比较，`storage.js:159-161/189-190`）；`SAVE_VER` 前跳且缺 `MIGRATIONS[2]` 时 `_migrate` **零步迁移照样盖章**（`:99-112`）；`SaveSystem.save` 不写任何戳（`:165-173`）；数组/标量型键天生无版本通道（`:159` 只处理非数组对象）。
