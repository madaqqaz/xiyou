# 《逆道西行》整改意见书（V8.40 基线）

> 基于代码全量审读 + 游戏系统全景分析，涵盖架构、玩法、UI、数值、内容、市场六大维度。
> 标记约定：🔴 P0 阻塞/高风险 · 🟡 P1 重要优化 · 🟢 P2 改善建议 · ⚪ P3 远期规划

---

## 一、架构整改

### 1.1 🔴 game.js 单文件膨胀（5000+ 行）

**现状**：`game.js` 承载了状态机、战斗调度、劫灰坊、复合节点、教学战、破韧窗口、业藏录等全部核心逻辑，已严重超出单文件可维护阈值。

**问题**：
- 任何修改都有连锁风险（如上次 `_compoundTrial` 教学战修复需在2600行处精确定位）
- 多人协作必然冲突
- 无法做单元测试隔离

**整改方案**：
| 拆分目标 | 来源 | 行数估算 |
|----------|------|----------|
| `game-core.js` | 状态机主循环、节点进入/离开、render调度 | ~1200 |
| `game-combat.js` | fight()、战后结算、破韧窗口、临阵操作 | ~800 |
| `game-ash.js` | 劫灰坊购买/升级/标记 | ~200 |
| `game-tutorial.js` | 教学战触发/恢复/六道教学 | ~300 |
| `game-map.js` | 地图生成委托、节点选择、路线验证 | ~400 |
| `game-legacy.js` | 业藏录、舍利塔、轮回殿等长线系统 | ~600 |

**优先级**：P0 — 建议在下一个功能版本前完成，否则后续每新增系统都会加剧债务。

### 1.2 🟡 全局命名空间 NDX 污染

**现状**：14个JS文件全部向 `window.NDX` 挂载属性，存在命名冲突风险（如 `NDX.pick` / `NDX._pick` / `NDX.ui` 等散落定义）。

**整改方案**：
- 短期：建立 `NDX` 命名空间注册表文档，列出每个文件挂载的所有 key
- 中期：各模块改为 IIFE 返回对象，由 `main.js` 统一组装：
  ```javascript
  // data.js
  const DataModule = (function() { ... return { WUXING, DIFFICULTY, ... }; })();
  // main.js
  Object.assign(NDX, DataModule, CombatModule, ...);
  ```
- 长期：ES Module 化（需构建工具支持）

### 1.3 🟡 存档系统脆弱性

**现状**：`save_system.js` 已集中管理 key，但仍基于 `localStorage`，存在以下风险：
- 浏览器清理/隐私模式丢失
- 存档体积上限（localStorage 约 5MB）
- 无版本迁移测试覆盖

**整改方案**：
- P1：增加存档导出/导入功能（JSON 文本 → 剪贴板/文件）
- P1：增加存档版本迁移的自动化测试
- P2：接入 IndexedDB 作为主存档后端（localStorage 降级为备份）
- P3：云存档（需后端支持）

### 1.4 🟢 新模块已开始拆分但未完成

**现状**：V8.40 已新增 `dao_system.js`、`attr_calc.js`、`battle_resource.js`、`save_system.js` 四个独立模块，但核心逻辑仍在旧文件中（如 `data.js` 仍有道途计算、`combat.js` 仍有属性计算）。

**整改方案**：
- 制定渐进迁移计划：每个模块标注"已迁移/未迁移/部分迁移"
- 迁移时保留旧接口作为别名，标记 `@deprecated`，下个版本移除

## 二、玩法整改

### 2.1 🔴 系统复杂度膨胀——新手认知过载

**现状**：第一章开局即暴露 15+ 系统（六道、五行、套装、灵宠、劫印、劫灰、心魔、寿命、法宝、隐藏职、流派特质、难度、战斗统计、佛经、成就），远超同类肉鸽的首局信息量。

**整改方案**：**渐进解锁机制**

| 章节 | 解锁系统 | 玩家感知 |
|------|----------|----------|
| 第1章 | 六道抉择 + 战斗 + 劫印（3选1） | "我选了一条路" |
| 第2章 | 装备 + 套装共鸣 | "装备有套装效果" |
| 第3章 | 灵宠进化 + 法宝充能 | "宠物能进化" |
| 第4章 | 五行克制 | "怪物有弱点" |
| 第5章 | 寿命系统 + 心魔/道心 | "寿命是资源" |
| 第6章 | 劫灰坊 + 轮回殿 | "死亡也有收获" |
| 通关后 | 隐藏职 + 流派特质 + 地狱难度 | "还有这么多可探索" |

**实现方式**：
- `data.js` 新增 `NDX.SYSTEM_UNLOCK` 表：`{ system: 'wuxing', unlockAct: 4, ... }`
- `ui.js` 渲染时检查 `s.act >= unlockAct`，未解锁系统不显示入口/提示
- 未解锁系统的劫印/装备掉落仍正常生成，但UI上标注"尚未领悟"（灰显），避免丢失进度

### 2.2 🟡 战斗节奏偏慢

**现状**：回合制 + 纯文字演出，单局时间可能超过 30 分钟，不符合移动端碎片化场景。

**整改方案**：
1. **战斗加速 2x/4x**：`fightSpeed` 已有框架，扩展为影响实际回合结算速度（而非仅演出速度）
2. **扫荡机制**：当战力碾压（atk > 怪物hp × 3）时，提供"一击扫荡"选项，跳过战斗演出
3. **Boss 战保留完整演出**：精英/Boss 锁 1x，保证体验

### 2.3 🟡 死亡/坐化后缺乏"再来一局"驱动力

**现状**：死亡后直接回到标题，缺乏"本局收获"总结。

**整改方案**：
- 死亡画面增加"此行收获"面板：
  - 获得的劫灰数量
  - 解锁的成就/图鉴条目
  - 离隐藏职还差多少（如"再击败3个精英即可觉醒破军"）
  - "再来一局"大按钮（比"返回标题"更醒目）
- 劫灰坊在死亡后立即可用（当前需回长安才能用）

### 2.4 🟢 八十一难内容差异化验证

**现状**：`trials81.js` 中 81 难结构完整（每难有 name/dark/intro/options/hidden），但需验证：
- 是否所有 81 难都有独特的 `dark`（黑暗独白）文案？
- `options` 的抉择后果是否真正影响后续路径（而非仅影响单次奖励）？
- 中后期（难 40-81）是否存在"换皮难"？

**整改方案**：
- 编写自动化脚本，扫描 `TRIAL_LIB` 中 `dark` 文案的重复率
- 为每难的 `options` 标注 `consequenceType`（immediate/chain/hidden），区分单次奖励与长线影响
- 中后期难至少 30% 应有链式后果（影响后续 2-3 难的选项/敌人/掉落）

## 三、UI/界面整改

### 3.1 🔴 横屏适配缺失

**现状**：CSS 断点全部基于竖屏宽度（xs≤380 / sm≤520 / md≤720 / lg≤768 / xl≤900），`.frame` 使用 `flex-direction: row`（左地图右面板），但横屏时 `#mid` 固定 `max-width: 420px` 导致面板过窄。

**整改方案**：
```css
/* 横屏适配 */
@media (orientation: landscape) and (max-height: 500px) {
  .frame {
    flex-direction: column;  /* 横屏时上下布局 */
    gap: 8px;
  }
  #mid {
    max-width: none;
    flex: 0 0 auto;
    max-height: 45vh;
  }
  #trail {
    flex: 1 1 auto;
    min-height: 50vh;
  }
}
```

### 3.2 🟡 战斗演出视觉层次不足

**现状**：战斗为纯文字 + 数值飘字，缺乏受击反馈、技能特效、破韧动画。

**整改方案**（按优先级）：
1. **受击闪烁**：英雄/怪物受击时头像/血条闪红（CSS `animation: shake 0.3s`）
2. **克制提示**：五行克制时伤害数字前加 `↑` 图标 + 金色，被克加 `↓` + 灰色（不仅靠颜色，也靠方向符号，色觉友好）
3. **破韧动画**：Boss 韧性条破碎时播放裂纹扩散 SVG 动画
4. **暴击/绝招演出**：暴击数字放大 1.5x + 短暂屏幕震动；绝招全屏暗化 + 特写

### 3.3 🟡 地图节点状态动画缺失

**现状**：地图节点为静态 PNG 图标，已通过/可选/锁定三种状态仅靠 CSS 透明度区分。

**整改方案**：
- 可选节点：微弱脉冲动画（`animation: pulse 2s infinite`）
- 已通过节点：灰显 + 微弱暗化
- 当前节点：金色边框 + 呼吸光效
- 锁定节点：完全灰显 + 锁图标叠加

### 3.4 🟢 信息密度优化

**现状**：手机竖屏下，地图 + 背包 + 劫印面板 + 战斗信息同时展示，可用空间极度紧张。

**整改方案**：
- 采用"抽屉式"面板：默认只显示地图 + 顶部状态条，背包/劫印/图鉴为侧滑抽屉
- 战斗时全屏沉浸，非战斗时可展开详情面板
- 关键信息（血量/战意/经力/寿命）常驻顶部 HUD，其余按需展开

### 3.5 🟢 五行克制信息可视化

**现状**：五行克制关系仅在 `data.js` 中定义（`NDX.WUXING.COUNTER`），UI 上缺乏直观展示。

**整改方案**：
- 战斗界面增加五行克制关系小图标（克制↑/被克↓/无关—）
- 设置菜单增加"五行相克图"参考页（圆形五角星图）
- 怪物信息卡显示五行属性 + 弱点提示

## 四、数值整改

### 4.1 🟡 五行克制幅度需模拟验证

**现状**：克制 +40% / 被克 -20%，数值来源为设计直觉，未经战斗模拟验证。

**风险**：
- +40% 可能导致克制方伤害爆炸（叠加套装共鸣 + 劫印 + 绝招后）
- -20% 可能导致被克方伤害过低，体验沮丧

**整改方案**：
1. 编写战斗模拟脚本（Monte Carlo 1000局），对比"有五行"vs"无五行"的通关率/平均回合数
2. 验证极端场景：克制方 + 破军套装 + 战道劫印 + 绝招 的伤害上限是否超过 Boss 血量的 50%
3. 如超限，考虑将 COUNTER_BONUS 从 0.40 降至 0.30，或改为加法区（与套装乘区分开）

### 4.2 🟡 套装共鸣乘区叠加风险

**现状**：`combat.js` 套装共鸣在"装备基础值累加之后、劫印/事件 bonus 之后统一结算（乘区叠加）"。

**风险**：多乘区叠加可能导致后期伤害/防御数值指数增长。

**整改方案**：
- 为每个乘区设置上限（如套装共鸣总加成不超过 +100%）
- 或改为加法区叠加（收益递减，更易平衡）
- 编写极端场景模拟：3件套 + 满劫印 + 满劫灰 + 终极特质 的伤害上限

### 4.3 🟡 六道 Build 平衡性

**现状**：六道专职属性差异明显（战道 atkPct:0.42 vs 缘道 atkPct:0.1），但缺乏通关率数据验证。

**整改方案**：
- 收集内测数据：各道通关率/平均通关回合数/平均死亡章节
- 如某道通关率显著低于其他（< 60%），考虑增强其核心机制而非简单加数值
- 特别关注隐道（闪避流）：闪避上限需有硬 cap，避免 100% 闪避无敌

### 4.4 🟢 怪物数值曲线平滑性

**现状**：`MONSTER_TABLE` diff 1-20 线性爬升，但 diff 13→14 出现 atk 停滞（116→118），diff 14→15 也仅 118→125。

**整改方案**：
- 绘制 diff-atk/hp 曲线，检查是否存在断崖/平台
- Boss（diff 20）的 atk 185 vs diff 19 的 160 差距合理，但 hp 2100 vs 1940 差距偏小
- 建议 Boss hp 提升至 2500-3000（配合破韧机制，保证 Boss 战 5-8 回合）

## 五、内容整改

### 5.1 🔴 index.html title 编码乱码

**现状**：`index.html` 第6行 title 标签内容为乱码（UTF-8 BOM + 错误编码混合）。

**整改**：
```html
<title>逆道西行 · 灵山终 · Demo</title>
```

### 5.2 🟡 zhuanjie.js 注释编码损坏

**现状**：`zhuanjie.js` 头部注释存在大量 `?` 替代中文字符（编码损坏），如"六道专职转职子系统（集中条件?+ 事件判定点）"。

**整改**：恢复注释中的中文内容，或重写为英文注释。

### 5.3 🟡 字符串国际化预留

**现状**：用户可见中文散落在 14 个 JS 文件中，无集中管理。

**整改方案**：
1. 短期：建立 `locale/zh-CN.js` 字符串表，各模块通过 `NDX.t('key')` 引用
2. 中期：`trials81.js` 的 `dark`/`intro`/`options.text` 已是数据驱动，可直接迁移
3. 长期：`events.js`/`enemies.js` 中的硬编码中文需逐步提取

### 5.4 🟢 _patch_driveFight.cjs 文件缺失

**现状**：`index.html` 未引用此文件，但文件系统中不存在，可能是已删除的补丁文件。

**整改**：确认是否已合并到 `combat.js`，如已合并则忽略；如未合并则恢复。

## 六、市场与运营整改

### 6.1 🟡 缺乏社交传播点

**现状**：H5 游戏的核心增长引擎是分享，当前无任何分享机制。

**整改方案**：
1. **死亡/通关一句话总结**：
   - "金蝉坐化于火焰山，享年 280 寿，逆道值 23，此行破 47 难"
   - 生成带水墨风格背景的分享图（Canvas → Image）
2. **稀有事件截图**：隐藏职觉醒、首次通关等时刻自动生成分享图
3. **功德榜社交化**：当前功德榜为本地数据，需接入后端排行榜

### 6.2 🟡 缺乏中期目标锚点

**现状**：长线目标（全成就/全隐藏职）过于遥远，10-20 局后留存断崖。

**整改方案**：增加中期里程碑
| 里程碑 | 解锁内容 | 预期达成局数 |
|--------|----------|-------------|
| 通关第2章 | 解锁第2英雄（悟空） | 3-5局 |
| 首次转职 | 解锁转职回忆录 + 专属外观 | 5-8局 |
| 集齐首套3件套装 | 解锁套装图鉴条目 | 3-6局 |
| 通关第4章 | 解锁五行克制提示 | 8-12局 |
| 首次坐化 | 解锁劫灰坊 + "再来一局"引导 | 2-4局 |

### 6.3 🟢 平台适配

**现状**：纯 H5，在 iOS 微信 WebView 中性能受限。

**整改方案**：
- 短期：优化战斗演出 DOM 操作（减少 innerHTML 重建，使用 DOM diff）
- 中期：打包为 Tauri/Electron 桌面端（Steam 发行）
- 长期：微信小游戏适配（需改造加载方式）

## 附录A：立绘体系专项补充

> 基于 enemies.js L844-1205（MONSTER_PORTRAITS / MONSTER_TAG_PORTRAITS / PORTRAIT_KEYWORDS / portraitOf() / NPC_PORTRAITS / HERO_EVOLVE_PORTRAITS）、data.js L2960-3030（HEROES 定义）、ui.js L3730-3850（战斗渲染层）、style.css L6810-6980（战斗动画）的深度审读。

### A.1 🔴 英雄转职立绘仅唐僧一人完整

**现状**：`HERO_EVOLVE_PORTRAITS` 仅定义了 `tangseng` 的 5 阶段立绘（base/evil/tier1/tier2/final），其余 4 英雄（悟空/八戒/小白龙/沙僧）完全缺失转职立绘映射。

**影响**：
- `game.js getHeroPortrait()` 对其他英雄只能回退到 `hero.portrait`（基础立绘），转职后视觉无变化
- 玩家完成一转/二转/终转后，英雄头像/战斗立绘/HUD 肖像均不更新，严重削弱转职成就感
- `data.js` 中仅唐僧定义了 `evolvePortraits` 字段，其余英雄无此字段

**整改方案**：
1. **紧急**：为 4 英雄补齐 `HERO_EVOLVE_PORTRAITS` 映射 + `data.js` 中 `evolvePortraits` 字段
2. 每英雄至少 3 阶段（base → tier1 → final），evil/tier2 可后续补齐
3. 资源命名规范：`{英雄中文名}一转.png` / `{英雄中文名}二转.png` / `{英雄中文名}终转.png`（与唐僧保持一致）
4. `getHeroPortrait()` 增加防御性检查：若转职立绘路径无效，回退到 `hero.portrait` 并 console.warn

**优先级**：P0 — 转职是核心玩法循环，视觉反馈缺失 = 功能半成品

### A.2 🟡 小怪立绘视觉重复（80+ 种 → 12 张轮换）

**现状**：`portraitOf()` 四级回退解析中，小怪立绘覆盖情况：

| 层级 | 覆盖范围 | 立绘数量 | 视觉差异 |
|------|---------|---------|---------|
| 精确名 `MONSTER_PORTRAITS` | 80+ 小怪名 | 4 张 webp（巡山小妖/拦路山魈/藤缠夜叉/尸煞妖童） | 极低：同阵营小怪完全相同 |
| 阵营标签 `MONSTER_TAG_PORTRAITS` | 8 阵营标签（妖/水/鬼/火/木/虫/魔/怪） | 8 张 webp | 中等：按阵营区分，但同阵营内无差异 |
| 关键词 `PORTRAIT_KEYWORDS` | Boss/精英名 | 不覆盖小怪 | — |
| 类型兜底 | mob | 1 张（巡山小妖） | 无差异 |

**问题**：
- 第 1 地区小怪（妖鼠/山魈/夜叉）全部显示同一张"巡山小妖"立绘
- V8.35 阵营标签立绘缓解了跨阵营重复，但同阵营内（如"妖"标签下的妖鼠+妖蛇+妖蛙）仍完全相同
- 精英怪回退到 `mon_elite_chizong_yaoshuai.webp` 一张通用精英立绘，所有精英视觉无差异

**整改方案**：
1. **短期（P1）**：按地区为小怪分配不同阵营标签组合，增加视觉区分度
   - 例：第 1 地区妖鼠 → `['妖', '兽']`，妖蛇 → `['妖', '虫']`，利用现有 8 张阵营立绘交叉组合
2. **中期（P1）**：为每地区前 3 种高频小怪生成专属立绘（约 17 地区 × 3 = 51 张）
   - 优先级：第 1-3 地区（玩家首印象）> 第 4-8 地区 > 后续地区
3. **长期（P2）**：精英怪专属立绘（每地区 1 张，约 17 张）
4. `portraitOf()` 增加地区感知参数：`portraitOf(name, type, boss, tags, region)`，同阵营不同地区可分配不同底色/边框

### A.3 🟡 立绘 onerror 兜底不完善

**现状**：
- Boss 大立绘 `fb-foe-art-img`：onerror 仅 `this.style.visibility='hidden'`，隐藏后怪物侧完全空白
- 英雄头像 `fb-avatar you`：onerror 仅 `this.style.visibility='hidden'`，隐藏后玩家侧无头像
- HUD 肖像 `hud-portrait`：onerror 仅 `this.style.visibility='hidden'`
- NPC 立绘：`npcPortraitOf()` 返回空字符串时无任何视觉反馈

**整改方案**：
```javascript
// 推荐：onerror 回退到类型默认图，而非隐藏
onerror="this.onerror=null; this.src='assets/Boss.png'"  // Boss
onerror="this.onerror=null; this.src='assets/小怪.png'"  // 小怪
onerror="this.onerror=null; this.src='img/hero_default.png'"  // 英雄
```
- 为每类角色准备 1 张 SVG 占位图（带角色类型文字标识），避免加载失败时视觉空白
- `npcPortraitOf()` 返回空时，渲染一个带 NPC 名首字的圆形占位

### A.4 🟢 立绘资源加载性能

**现状**：
- 地图节点图标已使用 `loading="lazy" decoding="async"`（ui.js L12-26）
- 战斗立绘（Boss 大图/英雄头像/怪物头像）**未使用懒加载**，每次进入战斗都同步请求
- 同一怪物多次出现时无缓存策略，重复请求相同立绘

**整改方案**：
1. Boss 大立绘 `<img>` 添加 `loading="lazy" decoding="async"`
2. 英雄头像/怪物小头像因尺寸小（< 50KB），可预加载到内存缓存（`Map<string, HTMLImageElement>`）
3. 首次加载后缓存 Blob URL，后续战斗直接使用缓存

## 附录B：战斗演出专项补充

> 基于 ui.js L3730-3850（战斗渲染层）、style.css L6810-6980（战斗动画）、main.js L980-994（技能演出调度）、combat.js（战斗内核）的深度审读。

### B.1 🔴 受击动画层次不足——仅 shake + flash 两层

**现状**：战斗受击反馈仅有：
- `hit-shake`：0.32s 水平抖动（`fbHitShake`，translateX ±7px + rotate ±1.5deg）
- `hit-flash`：0.3s 红色闪光（`fbHitFlash`，rgba(200,40,40,.45) 渐隐）
- 攻击方 `fb-strike`：0.4s 亮度闪光（`fbStrikeFlash`，brightness 1→1.35→1）

**问题**：所有伤害类型（普攻/暴击/克制/破韧/绝招/DoT）共用同一套受击动画，无法从视觉区分伤害类型。

**整改方案**——按伤害类型分层动画：

| 伤害类型 | 当前 | 目标 | CSS 方案 |
|---------|------|------|---------|
| 普攻 | hit-shake + hit-flash | ✅ 保持 | 现有 |
| 暴击 | 同普攻 | 数字放大 1.5x + 屏幕微震 + 金色闪光 | `.fb-float.crit` 已有样式，增加 `@keyframes fbScreenShake` |
| 五行克制 | 同普攻 | 元素色闪光（火→红/水→蓝/木→绿/金→白/土→黄）+ 克制箭头动画 | 新增 `.hit-wuxing-{element}` 类 |
| 被克 | 同普攻 | 灰色弱闪光 + 伤害数字缩小 0.8x | 新增 `.hit-resist` 类 |
| 破韧 | 仅 fbBreakGlow | 裂纹扩散 + 碎片飞散 + Boss 震退 + 全屏白闪 | 已有 `fbToughBreak`/`fbCuCrack`/`fbCuFlash` 关键帧，需接入 |
| 绝招/法宝 | 无专属 | 全屏暗化 0.5s → 特写立绘 → 伤害数字 | 新增 `.fb-ult-cinematic` 遮罩层 |
| DoT/反震 | 同普攻 | 紫色/橙色脉冲（非抖动） | 新增 `.hit-dot` / `.hit-reflect` 类 |

**实现要点**：
- `ui.js renderBattle()` 中根据 `cur` 回合数据的伤害类型，给受击方添加对应 CSS 类
- `combat.js` 输出回合数据需增加 `dmgType` 字段（'normal'/'crit'/'wuxing'/'break'/'ult'/'dot'/'reflect'）

### B.2 🟡 技能演出仅有 CSS 类切换，缺乏信息层

**现状**：`main.js L987-994` 技能演出逻辑：
```javascript
side.classList.remove('skill-atk', 'skill-chant', 'skill-ult');
void side.offsetWidth; // 强制重绘
side.classList.add('skill-' + kind);
setTimeout(() => side.classList.remove(...), 800);
```
- 3 种技能动画（`skillAtkLunge` / `skillChantGlow` / `skillUltBurst`），时长固定 800ms
- 无技能名称飘字、无技能图标、无敌方受击对应演出

**整改方案**：
1. **技能名称飘字**：技能触发时，在立绘上方显示技能名（如"金睛破甲""慈悲愿力"），1.2s 渐隐
   - 数据来源：`NDX.HEROES[id].passive` 已有 trait 描述，需新增 `skillName` 字段
2. **技能图标覆盖**：技能触发时，在碰撞区 `fb-clash` 显示技能专属图标（金箍/袈裟/钉耙等），0.8s 缩放渐隐
3. **敌方受击对应**：玩家技能攻击时，敌方播放对应受击动画（见 B.1 分层方案）
4. **动画时长差异化**：atk 600ms / chant 1000ms / ult 1500ms，与技能节奏匹配

### B.3 🟡 破韧窗口演出简陋

**现状**：破韧成功仅有 `fbBreakGlow`（亮度 1→1.8→1），已有但可能未完全接入的动画：
- `fbToughBreak`：韧性条破碎动画
- `fbCuCrack`：裂纹缩放旋转
- `fbCuFlash`：裂纹闪光
- `fbToughBurst`：韧性碎片飞散

**问题**：两相劫·破韧窗口是核心玩法高潮（限时法宝破韧→领厚赏），但视觉反馈不足以传达"关键时刻"的紧张感。

**整改方案**——破韧演出时间轴：
```
0.0s  韧性条归零 → fbToughBreak 播放（裂纹扩散）
0.3s  全屏白闪 → fbCuFlash（0.3s）
0.5s  Boss 震退 + hit-shake（0.4s，幅度加大至 ±12px）
0.8s  碎片飞散 → fbToughBurst（0.6s）
1.0s  法宝选择界面弹出（限时 2s 倒计时）
1.5s  若超时 → 挂机兜底提示 + 灰色遮罩
2.0s  若破韧成功 → 金色光柱 + Boss 硬直动画（1s）
3.0s  阶段奖励飘字 + 继续战斗
```

### B.4 🟡 Boss 多阶段演出断层

**现状**：两相劫 Boss 阶段切换（`combat.js` `stageBreakPoint`）时，仅文字日志提示"阶段X→阶段Y"，无视觉过渡。

**整改方案**：
1. 阶段切换时播放 Boss 变身动画（立绘闪白→缩放→新立绘淡入），1.5s
2. 全屏暗化遮罩 + 阶段名飘字（如"第二相·金刚怒目"）
3. `MONSTER_PORTRAITS` 中同一 Boss 的多阶段名（如"白骨夫人·三戏之身""白骨夫人·尸魔真身"）应映射不同立绘，而非全部指向同一张 `boss_baigujing.png`

**当前问题**：白骨夫人 8 个变体名全部映射到 `boss_baigujing.png`，红孩儿 3 个变体全部映射到 `boss_honghaier.png`，视觉无变化。

### B.5 🟡 战斗信息层次缺失

**现状**：战斗界面信息密度高但层次不清：
- 伤害飘字仅有颜色区分（crit 金色/hurt 橙色/miss 灰色/dodge 蓝色/dot 紫色/reflect 红色/heal 绿色/shield 黄色）
- 无伤害构成分析（物理/法术/克制/暴击各占多少）
- 无回合统计面板
- 无战斗日志回看

**整改方案**：
1. **伤害构成饼图**：战斗结算时显示伤害来源占比（物攻/法攻/克制/暴击/DoT/反震）
2. **回合统计条**：血条下方显示"回合 N / 预计 M"（基于 DPS 估算）
3. **战斗日志折叠面板**：战斗结束后可展开查看每回合详细日志
4. **五行克制动态提示**：攻击时在碰撞区显示克制关系箭头（↑克制/↓被克/—无关），不仅靠弱点图标

### B.6 🟢 战斗节奏控制不足

**现状**：
- `fightSpeed` 仅有 1x/2x 两档，2x 仅影响演出间隔
- 无自动战斗（挂机）选项
- 无扫荡机制（碾压时跳过战斗）
- Boss/精英锁 1x（整改意见书 2.2 已提及）

**补充方案**：
1. **4x 加速**：影响实际回合结算速度（跳过动画，仅保留结果飘字）
2. **自动战斗**：AI 自动选择最优操作（普攻/技能/法宝），玩家可随时接管
3. **扫荡**：当 `player.atk > monster.hp × 3` 时，战斗开始前显示"一击扫荡"按钮，直接结算
4. **Boss 战保留完整演出**：扫荡/4x 对 Boss/精英无效
