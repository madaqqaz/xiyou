# 《逆道西行》全面分析报告

> 版本基准：v=341（2026-09-06）
> 分析范围：代码真源（`demo/js/`、`demo/css/`）、数据注册表、浏览器实机取证、资源资产清单
> 分析视角：从业者（架构/系统/数值/工程）+ 玩家（体验/节奏/沉浸/留存）

## 一、执行摘要

《逆道西行》是一款以黑暗西游为题材的单局 Roguelike 肉鸽构筑游戏，纯前端 H5 原生 JS 实现，零构建零依赖，三端同步开发（浏览器 H5 / 微信小游戏 / TapTap 买断）。

**核心判断：系统骨架庞大且完整，但内容填充与体验打磨存在明显断层。**

| 维度 | 评级 | 一句话结论 |
|---|---|---|
| 系统架构 | B+ | 277个NDX注册表、38044行JS，系统覆盖极广，但耦合度高、owner边界模糊 |
| 内容量 | B- | 301装备/143事件/38成就/64转职数据丰富，但81难仅22难有专属剧情、敌人种类偏少 |
| 战斗体验 | C+ | 公式完整、有意图提示/教学引导，但立绘静态无动画、打击感弱、操作反馈不足 |
| 视觉美术 | B | 暗金水墨风格统一、立绘资源充足（英雄39/敌人66/Boss31），但UI组件偏粗糙、战斗布局有空白 |
| 音频 | D | 仅8个音频文件，无BGM/无音效/无环境音，沉浸感严重缺失 |
| 肉鸽核心 | B | 六道/劫印/经文/装备/寿数/心魔多维度构筑，但六道区分度不足、配额机制刚落地待验证 |
| 完成度 | 65% | 核心循环可跑通，但中后段内容模板化、数值未平衡、多周目继承待实装 |
| 上线准备度 | C | 三端适配层已建，但微信首包/性能/审核合规/TapTap成就均未实际验证 |

**最紧迫的三个问题（P0）：**
1. **战斗打击感几乎为零**——立绘全程静态、无攻击前冲/受击位移/伤害飘字/屏幕震动，玩家"看数字跳动"而非"在打架"，这是肉鸽游戏留存的致命伤。
2. **81难内容断层**——仅前20难有专属剧情数据，21-81难依赖动态生成/模板复用，中后段体验同质化严重，与"八十一难"的卖点承诺不符。
3. **音频完全缺失**——无BGM/无攻击音效/无UI反馈音，在移动端静音率虽高，但有声场景下体验差距巨大，且影响TapTap买断版的产品完成度感知。

## 二、项目概况与技术栈

### 2.1 基本信息

| 项 | 值 |
|---|---|
| 产品名 | 逆道西行（nidao-xiyou） |
| 题材 | 黑暗西游 · 单局 Roguelike 肉鸽构筑 |
| 技术栈 | 原生 HTML + CSS + ES6+ JavaScript，零构建、零第三方运行时依赖 |
| 代码规模 | JS 102文件 / 38,044行；CSS 1文件 / 15,159行；index.html 21.5KB |
| 系统注册表 | 277个 `NDX.XXX` 定义 |
| 入口 | `demo/index.html`（浏览器双击可玩，推荐HTTP服务） |
| 三端 | 浏览器H5（主线）、微信小游戏（web-view嵌H5）、TapTap买断（离线+成就） |
| 当前版本 | v=341 |

### 2.2 代码架构

**加载顺序**（index.html 按序加载102个JS）：
```
storage.js → platform/{browser,taptap,wechat}.js → data_*.js(35个) →
events.js → equipment.js → enemies.js → combat.js → game_*.js(拆分) →
ui_*.js(拆分) → achievements.js → sound.js → main.js(最后)
```

**模块分层**：
- **数据层**（`data_*.js`，35个文件）：英雄/装备/劫印/经文/敌人/Boss/81难/事件/成就/地区/转职/宠物/材料/朝代/寿数/配额/镜像/谈判/天道/好感/存档/轮回等，全部注册到全局 `NDX` 对象。
- **逻辑层**（`game_*.js`、`combat.js`、`equipment.js`、`events.js`）：Game状态机、战斗引擎、装备管理、事件执行、存档系统。
- **渲染层**（`ui_*.js`）：UI渲染、面板弹窗、战斗界面、地图渲染。
- **入口层**（`main.js`）：事件委托、startGame、onAppClick。

**架构优点**：
- 纯原生JS零依赖，加载快、兼容性好、三端移植成本低。
- data.js 已拆分为35个 `data_*.js`，按功能域模块化，可维护性提升。
- 全局 `NDX` 命名空间统一，避免全局污染。
- 平台适配层（`platform/`）已建立，三端差异隔离。

**架构问题**：
1. **CSS 单文件15159行**——未按组件/页面拆分，选择器冲突风险高，修改时全局影响面大。
2. **`NDX` 全局注册表277个**——缺乏统一的模块导出/导入机制，依赖加载顺序，新增系统时容易遗漏或重复。
3. **顶层别名约定脆弱**——已确立"顶层NDX别名只能用var不能用const/let"的铁律，但这是经典script共享全局词法环境的妥协，非真正的模块系统。
4. **game.js/ui.js 仍偏大**——虽已拆分出 `game_*.js`/`ui_*.js`，但 `combat.js`(2058行)、`events.js`(2221行)、`equipment.js`(2147行)、`main.js`(2032行) 仍是超2000行的大文件，职责边界可进一步细化。
5. **onAppClick try-catch 吞异常**——main.js 的点击事件处理器用 try-catch 包裹所有 action，运行时错误被静默吞掉，导致"点了没反应"时 console 无 error，排查极困难（本次"游戏无法进入"就是此问题）。

## 三、游戏设计完整度分析

### 3.1 核心循环

**设计意图**：选英雄 → 长安出发 → 地图节点选择（战斗/精英/事件/商店/休息/Boss）→ 战斗获取装备 → 抉择获取劫印/经文 → 寿数消耗压力 → 地区Boss → 多周目轮回继承。

**实际状态**：核心循环可跑通（已验证：首页→选英雄→地图→第一难教学战→抉择→后续节点），但中后段循环的内容填充和数值平衡未完成。

**玩家视角评价**：
- 前3难（金蝉遭贬→金蝉蒙冤→江流漂孤）+ 长安送行事件的教学节奏设计合理，"故事代入→系统教学→正式开战"的分散教学思路正确。
- 但教学战之后，玩家进入正式战斗时，对"为什么选这个节点""劫印怎么搭配""经文有什么用"仍缺乏足够的正反馈引导。
- 寿数系统（27岁出发、节点耗寿、55大限）是独特的压力机制，但前期耗寿感知弱（0.2-0.3岁/节点），玩家可能到中期才意识到寿数是硬资源。

### 3.2 英雄系统

**数据**：5个英雄（取经人/孙悟空/猪八戒/沙僧/小白龙），仅取经人初始解锁，其余需通关取经人后解锁。

| 英雄 | 定位 | 主键 | 本命 |
|---|---|---|---|
| 取经人（唐僧） | 愿·法术系 | 经 | 金蝉谛听·慈悲 |
| 孙悟空 | 体·物理系 | （待确认） | （待确认） |
| 猪八戒 | 体·防御型 | （待确认） | （待确认） |
| 沙僧 | 愿·反伤型 | （待确认） | （待确认） |
| 小白龙 | 体·闪避型 | （待确认） | （待确认） |

**问题**：
1. **英雄解锁门槛过高**——需通关取经人一次才能解锁其他英雄，但取经人本身难度不低（白骨精为第一个超难关卡），新玩家可能在解锁第二个英雄前就流失。对标杀戮尖塔（初始解锁4角色）和万世剑冢（多角色初始可选），这个解锁策略偏保守。
2. **英雄差异化数据待确认**——vm沙箱加载后英雄的 homeDao/mainDao/series/type 字段均为 undefined，说明英雄数据结构可能用了不同字段名，或字段未填充。5个英雄的属性曲线、技能差异、本命法宝效果需要实际战斗验证。
3. **英雄立绘**：img/portraits/heroes 有39张（含转职/隐藏职立绘），资源充足。

### 3.3 六道/道途系统

**设计**：六道（渡/战/隐/夺/缘/逆），通过劫难抉择积累道途点数，影响属性加成和劫印/经文/装备的流派适配。

**数据**：`SEAL_DAOTU` 6条、`SUTRA_SIX_DAOS` 6条、`HERO_HOME_DAO`/`HOME_DAO_MULT` 等注册表存在。

**问题**：
1. **六道区分度不足**——用户已明确指出"我选贪就是想多刷怪，结果实现不了，不能多拿装备，导致6道的设计没有意义"。当前正在落地"地区配额制"（万世剑冢模式：必须满足X小怪/Y事件/Z精英才能刷地区Boss），但该机制刚实施，实际体验待验证。
2. **道途属性加成不透明**——玩家选了渡/战/隐后，能直观看到属性变化吗？从实机截图看，底部属性面板显示"攻78/愿200/善0/恶0"，但道途点数如何转化为属性加成，玩家缺乏清晰的认知路径。
3. **逆道/缘道/夺道的独特机制待强化**——渡道（法伤/诵经）和战道（物攻/杀敌）相对清晰，但隐道（闪避/偷袭）、夺道（掠夺/多刷）、缘道（NPC/事件收益）、逆道（逆经/反常规）的独特玩法机制需要更明确的系统支撑。

### 3.4 劫印系统

**数据**：`SEAL_DAOTU` 6条（道途）、`SEAL_WORDS` 47条（词条）、img/seals 47张图标。

**设计**：每难后获得劫印，劫印带道途标签和词条属性，生效格有限，同道途叠加形成流派。

**问题**：
1. **劫印品质字段不统一**——301件装备中280件品质字段为"?"（可能用 tier/level 等其他字段），劫印的品质体系（白/蓝/金/红）是否完整落地待确认。
2. **劫印获取节奏**——每难后获得劫印，81难意味着最多81个劫印，但生效格有限（第一章2格），中后期劫印溢出后的处理（合成/拆解/替换）需要清晰的UI和操作路径。
3. **劫印与道途的协同**——同道途劫印叠加是核心流派驱动力，但当前玩家是否能直观看到"我已激活3个渡道劫印，获得X加成"，需要UI层面的流派进度显示。

### 3.5 经文系统

**数据**：`SUTRA_SIX_DAOS` 6条（六道经文）、img/icons/sutras 25张图标。`SUTRA_FRAG`（渡道经文碎片）和 `NI_SUTRA_FRAG`（逆道经文碎片）在vm沙箱中为0，可能数据在其他变量名或动态生成。

**设计**：渡道事件/篝火获得经文，逆道获得逆道经文，经文根据数量对属性有不同加成（用户确认："根据数量多少加不同的属性"）。

**问题**：
1. **经文数据量待确认**——vm沙箱中 SUTRA_FRAG/NI_SUTRA_FRAG 均为0，只有 SUTRA_SIX_DAOS 6条。经文系统是用户强调的核心系统之一（"渡能获得经文，篝火能获得经文"），数据完整度需要核实。
2. **经文学习成本**——用户曾考虑"经文类似梦幻西游成品，独立碎片形式，合成整本自动生效，减少学习成本"，当前实现是碎片还是整本？如果是碎片合成，UI操作路径是否清晰？
3. **经文与劫印的功能重叠**——经文（数量加成）和劫印（词条加成）都提供属性加成，二者的差异化定位需要更清晰：劫印是"构筑选择"（有限生效格、流派搭配），经文是"积累奖励"（数量阈值、自动生效）。

### 3.6 装备系统

**数据**：`EQUIP_POOL` 301件，槽位分布：weapon(67)/treasure(65)/armor(64)/pet(32)/boots(32)/head(29)/component(6)/comp(4)/upg(2)。基础装备35件、冒险装备18件、套装13套。img/icons/equipment 114张图标。

**设计**：英雄专属4件套装（初始长安拿到基础套）→ 通用套装1阶段（2章）→ 英雄套装2阶（3-4章），可混搭散件。装备有槽位（兵/甲/冠/靴/宠/法宝/宝/印）。

**问题**：
1. **装备品质字段不统一**——301件中仅21件有明确品质（1品11/2品10），280件品质字段为"?"。这意味着装备的稀有度/掉落权重/升级路径可能未完整实现，或用了其他字段名。
2. **装备图标不足**——301件装备但只有114张图标，意味着大量装备共用图标或无图标，视觉辨识度低。
3. **装备路线与英雄专属/通用套装的层级**——用户设计了"英雄基础套 < 通用1阶 < 英雄2阶"的装备路线，但301件装备中如何分层、各层级的数量比例、掉落地区限制，需要数据层面的明确标记。
4. **宠物槽位32件**——装备池中pet槽位有32件，但宠物系统（PET_EVOLUTIONS 10条）相对独立，宠物作为"装备"穿在身上的设计是否与独立宠物系统冲突？

### 3.7 法宝系统

**数据**：`FABAO_POOL` 9件，img/icons/treasures 10张图标。

**问题**：
1. **法宝数量严重不足**——仅9件法宝，对于肉鸽构筑游戏来说太少。对标杀戮尖塔（遗物100+）、万世剑冢（法宝/法器50+），9件法宝意味着玩家每局的法宝选择高度重复，构筑多样性严重受限。
2. **法宝是主动技能**——战斗中手动祭出、有冷却，这是战斗操作的核心维度之一。9件法宝意味着战斗中的主动技能选择极少。
3. **英雄本命法宝**——`HERO_BENMING_FABAO` 注册表存在，每个英雄应有本命法宝，但9件总池中是否包含5个英雄的本命？如果本命法宝是固定的，那通用法宝只有4件可选。

### 3.8 寿数与心魔系统

**数据**：`NDX.LIFE`（START27/MAX55/RETURN_NEED6/MEDITATE_REGAIN0.3/COST耗寿表/WARN_AGE[22,15,8,3]）、`lifeCost()` 函数。

**设计**：27岁出发，每进一节点耗寿（mob0.2/trial0.3/elite0.5/boss0.6），55岁大限坐化，土地庙可回寿。恶道抉择增加心魔，心魔满100触发镜像战。

**评价**：
- 寿数系统是本游戏最独特的机制之一，将"时间压力"引入肉鸽，区别于杀戮尖塔的纯层数压力。
- 但前期耗寿感知弱（0.2-0.3岁/节点，前10难仅耗2-3岁），玩家可能到中期才意识到寿数是硬资源。建议前期通过教学/事件强化寿数感知。
- 心魔系统与恶道选择绑定，是"高风险高回报"的代价机制，但心魔满100后的镜像战惩罚是否足够平衡（不掉落/强制战），需要数值验证。
- RETURN_NEED=6（返程需6年）与用户设计文档的"回来九年"存在口径冲突，需确认。

### 3.9 转职系统

**数据**：`ZHUANJIE` 64条、`HIDDEN_JOBS` 6个隐藏职、`HERO_EVOLVE_PORTRAITS` 注册表。

**设计**：英雄一转（白骨精后触发）、二转/三转（后续地区），隐藏转职需满足特定劫难条件。

**问题**：
1. **64条转职数据的完整度**——64条是配置条目还是实际可触发的转职数量？5英雄×多阶转职×隐藏职，64条是否覆盖完整？
2. **转职触发条件透明度**——隐藏转职"满足关键劫难条件后觉醒"，但玩家如何知道条件？是完全隐藏（靠探索）还是有线索提示？对标万世剑冢的隐藏职业，通常有隐晦的线索但不直接说明。
3. **转职立绘**——img/portraits/heroes 39张（含转职立绘），img/portraits/special 16张，资源充足。

### 3.10 宠物与随从系统

**数据**：`PET_EVOLUTIONS` 10条、`DISCIPLE_LIB` 3个随从、img/portraits/pets 5张。

**问题**：
1. **宠物系统定位模糊**——用户说"宠物是独立的，先不考虑"，但装备池中pet槽位有32件、PET_EVOLUTIONS 10条，说明宠物系统已有部分实现。宠物是独立战斗单位还是装备型加成？需要明确定位。
2. **随从仅3个**——DISCIPLE_LIB 只有3个随从，对于81难/17地区的游戏来说偏少。随从系统（跟随玩家战斗的NPC）是否是核心玩法？如果是，需要扩充；如果不是，可简化。

### 3.11 81难与地区地图

**数据**：`TRIALS` 22条（对象，key为1-20 + wukong_liangjie + __xinmo）、`ACT_NAMES` 17个地区、`REGION_QUOTA` 17条配额、`BOSS_TABLE` 10个Boss、`ELITE_TABLE` 12个精英。

**地区列表**（17地区）：大唐境内→两界山→黑风山→高老庄→黄风岭→流沙河→四圣试禅→五庄观→白虎岭→宝象国→平顶山→乌鸡国→车迟国→通天河→金兜山→女儿国→火焰山→（后续待确认）

**重大问题**：
1. **81难仅22条专属剧情**——TRIALS对象只有22个key（1-20 + 2个特殊），意味着第21-81难没有专属剧情数据，依赖动态生成或模板复用。这是内容完成度的最大断层。
2. **17地区 vs 81难的密度**——81难分布在17地区，平均每地区4.8难。但前20难覆盖了多少地区？如果前3难（金蝉遭贬/金蝉蒙冤/江流漂孤）都在大唐境内，那地区密度不均。
3. **Boss仅10个**——17地区至少需要17个地区Boss（每地区一个），当前只有10个，意味着7个地区没有专属Boss，可能复用或缺失。
4. **精英仅12个**——同理，17地区的精英怪数量不足。
5. **普通敌人动态生成**——vm沙箱中 ENEMIES/ENEMY_TABLE/MOBS 均为0，说明普通怪物是基于地区/难度动态生成的（`BEHAVIOR_PROTOTYPES` 4个行为原型驱动），而非静态数据表。动态生成的好处是灵活，但坏处是敌人种类感弱、玩家对"这个怪有什么特性"缺乏认知。

### 3.12 事件系统

**数据**：`EVENTS` 143条、`FIXED_EVENT_LAYERS`/`FIXED_EVENT_TRIALS` 固定事件、`BONFIRE_RITES` 1条篝火仪典。

**评价**：
- 143个事件是内容量最充足的系统之一，覆盖战斗/抉择/奖励/惩罚/NPC互动等多种类型。
- 事件与六道抉择绑定，是道途点数和劫印/经文的主要获取来源。
- 但事件的重复率控制、地区专属事件分布、事件之间的关联性（呼应链）需要验证。用户提到"50难↔70难回响"的呼应链设计，是否已在143个事件中落地？

### 3.13 成就与收集系统

**数据**：`ACHIEVEMENTS` 38条、img/icons/achievements 50张图标、`ACH_VOLUMES`（成就卷册）、`DYNASTY` 2个朝代（夏/商）。

**设计**：通关成就、挑战成就、收集成就；朝代递进（夏→商→周→…→清），第一周目通关称"夏僧"；完美结局才能点亮经文成就。

**问题**：
1. **成就仅38条**——对于肉鸽游戏（杀戮尖塔成就100+），38条偏少。但成就图标有50张，说明可能有12个成就数据未填充或图标预留。
2. **朝代系统仅2个**——DYNASTY只有夏/商2个，用户设计是夏商周…清一直到清后循环，当前仅实现2个，中后段朝代缺失。
3. **成就与多周目继承**——成就是否提供跨周目加成（如杀戮尖塔的boss遗物解锁）？用户设计"回长安才能开局带1装备1劫印"，这是成就驱动的继承机制，但完整度待验证。

### 3.14 多周目与轮回系统

**数据**：`data_reincarnation.js`、`DEATH_UNLOCKS`、`CYCLE_KEY`、衣冠冢/舍利塔机制（用户设计）。

**设计**：战斗失败→下周目当前地区刷衣冠冢（选1件装备）；寿尽滞留→舍利塔（选1装备+1套经文）；回长安→开局带1装备1劫印；完美结局→点亮经文成就。

**评价**：
- 这是本游戏肉鸽核心的"死亡激励"机制，区别于杀戮尖塔的纯解锁、万世剑冢的继承点。衣冠冢/舍利塔/长安继承的三档设计有层次感。
- 但"只有回到长安才能开局带装备"意味着如果玩家在中期死亡，下周目几乎从零开始，挫败感可能较强。需要平衡"死亡惩罚"与"死亡激励"。
- 朝代递进（夏→商→…）是长期目标，但仅实现2个朝代，中后段缺失。

## 四、战斗系统深度分析

### 4.1 战斗架构

战斗引擎位于 combat.js（2058行），配合 game_combat_2.js、battle_resource.js、dao_system.js 等模块。战斗为回合制，玩家操作（攻/经/绝/法宝）+ 敌人AI行为循环。

**战斗流程**：
1. VS入场动画（玩家立绘 vs 敌人立绘）
2. 回合开始 → 敌人意图提示（攻击/格挡/狂暴）
3. 玩家操作（普攻/诵经/绝招/法宝/爆发/逃跑）
4. 结算 → 敌人行动 → 下一回合
5. 胜负判定 → 掉落/结算

### 4.2 技能设计

**当前技能**（CHANTS 5条 + 法宝9件 + 英雄本命）：

| 技能类型 | 数量 | 说明 |
|---|---|---|
| 普攻（攻） | 1 | 基础物理攻击，无冷却 |
| 诵经（经） | 1 | 法术攻击，CD2回合（用户反馈偏长） |
| 绝招（绝） | 1 | 终结技，敌人血量<30%可用 |
| 法宝 | 9件 | 主动技能，战斗中祭出，有冷却 |
| 爆发 | 1 | 气势爆发，满气势后释放 |

**问题**：
1. **技能数量严重不足**——核心战斗技能只有3个（攻/经/绝）+ 9件法宝，总计12个主动选择。对标万世剑冢（技能20+，含连招/组合技）、杀戮尖塔（每角色卡牌30+），本游戏的战斗操作维度极薄。
2. **诵经CD2回合偏长**——用户明确反馈"诵经2cd是不是太长了一点"。在3技能体系下，2CD意味着玩家有1/3的回合只能用普攻，节奏单调。建议改为1CD或引入"诵经层数"机制（连续诵经叠加法伤）。
3. **起手怪物先动手**——用户反馈"为什么起手是怪物先动手，体验不佳"。回合制游戏中玩家先动手是惯例（除非敌人有"先手"特性），起手被打会让玩家产生"失控感"。建议改为玩家先动手，或给敌人加"先手"标签并明确提示。
4. **缺乏连招/组合技**——万世剑冢的核心乐趣之一是技能连招（A技能接B技能触发额外效果），本游戏3个基础技能之间没有组合关系，法宝与基础技能也缺乏协同。
5. **技能升级/变异缺失**——肉鸽游戏的核心乐趣是"技能成长"（杀戮尖塔的卡牌升级、万世剑冢的技能强化），本游戏的攻/经/绝是否有升级路径？从数据看没有明确的技能升级系统。

### 4.3 战斗时长与节奏

**实测**（接引使者教学战）：
- 玩家HP 1300，敌人HP 1410
- 普攻伤害约163（玩家攻击78，敌人防御未知）
- 预计战斗时长：8-12回合，约2-3分钟

**问题**：
1. **普通战斗时长偏长**——2-3分钟一场普通战斗，对于肉鸽游戏（一局要打20-30场）来说总时长偏长（单局40-60分钟）。杀戮尖塔普通战斗约1-2分钟。
2. **节奏匀速无起伏**——战斗中缺乏"高潮时刻"（暴击/爆发/终结/连招），每回合都是"普攻→敌人攻击→诵经→敌人攻击"的匀速循环，玩家容易疲劳。
3. **战斗速度调节**——已有1x/2x/3x速度调节（set-fight-speed按钮），但默认1x，新玩家不知道可以加速。建议教学中提示加速功能，或默认2x。

### 4.4 打击感与反馈

**这是本游戏战斗体验的最大短板。**

**当前状态**（实机截图观察）：
- 立绘全程静态，无攻击前冲/受击位移/死亡动画
- 无伤害飘字（暴击/闪避/格挡无视觉区分）
- 无屏幕震动/hitstop（命中停顿）
- 无攻击弹道/刃光/技能特效
- 血条变化无动画（直接跳变）
- 无受击闪烁/变红
- 战斗日志有叙事性文字（"接引使者抢先扑来...堪堪擦过...皮肉之伤"），但文字无法替代视觉反馈

**对标万世剑冢的打击感要素**（用户明确要求借鉴）：
1. **攻击前冲（lunge）**——我方立绘translateX扑向目标，命中瞬间hitstop
2. **击退（knockback）**——敌方被击translateX后弹回
3. **受击位移**——短暂位移+弹回
4. **伤害飘字**——暴击大字/闪避/格挡/伤害数字弹出
5. **屏幕震动**——受击/爆发时震屏
6. **技能特效**——攻击弹道/刃光/粒子效果
7. **血条动画**——平滑过渡+受击闪烁
8. **高潮层**——识破/破韧/爆发/终结/Boss大招时慢镜+全屏闪光+大粒子+震屏+大字台词

**改善建议**（P0，零依赖CSS可落）：
- 立即实现"前冲+击退+受击位移"（CSS transform + keyframes），这是"人没动→人动了"的最大跃升
- 加伤害飘字（绝对定位div，CSS动画弹出+淡出）
- 加屏幕震动（body或战斗容器的animation shake）
- 加血条平滑过渡（transition: width 0.3s）
- 加受击闪烁（filter: brightness(2) + 快速恢复）

### 4.5 敌人AI与行为

**数据**：BEHAVIOR_PROTOTYPES 4个行为原型、ENEMY_BEHAVIOR_MAP 行为映射、_smoke_monster_behavior.js 29项测试通过。

**设计**：敌人有pattern循环/技能池加权/低血阶段切换/guard·buff/意图预告/教学战纯普攻。

**评价**：
- 敌人AI系统的架构完整，有行为原型、意图预告、阶段切换，对标杀戮尖塔的敌人设计。
- 但行为原型仅4个，意味着敌人的行为模式同质化严重（大部分敌人是"攻击→攻击→技能"的循环）。需要扩充行为原型（如：连续攻击型、蓄力型、召唤型、护盾型、狂暴型、治疗型等）。
- 意图预告（敌人头顶显示下一步动作）已实现，这是杀戮尖塔的核心设计，正确。

### 4.6 战斗教学引导

**设计**：接引使者教学战，观音菩萨逐回合引导（先点攻→再点经→最后点绝），气泡式提示≤15字。

**实机观察**：
- 观音菩萨头像+气泡出现在战斗界面顶部，引导文字清晰
- 第一回合引导"先点【攻】--普攻降妖，观其血线..."
- 教学战纯普攻（敌人行为受限）

**评价**：
- 教学引导的设计思路正确（互动式、逐回合、短提示），比弹窗说明书好得多。
- 但观音气泡的位置在战斗界面顶部，可能遮挡敌人血条/意图，需要调整位置或加半透明背景。
- 教学战结束后，玩家进入正式战斗时是否有"进阶提示"（如"试试法宝""注意敌人意图"）？从实机看没有，新玩家可能在教学战后直接面对正式战斗而不知所措。

### 4.7 战斗UI布局

**实机观察**（战斗进行中截图）：
- 顶部：敌人名称+头像+血条+回合数
- 左侧：玩家立绘（较小，左下角）+绿色血条
- 右侧：敌人立绘（较大）+红色血条+意图提示
- 右侧操作栏：爆发/攻击/技能/选择技能（竖排，图标偏小）
- 底部：战斗日志（叙事性文字）+回合统计
- 中间：水墨山水战斗背景

**问题**：
1. **布局不对称**——玩家立绘在左下角较小，敌人立绘在右侧较大，视觉重心偏右，玩家缺乏"我在战斗"的代入感。
2. **操作栏偏小且文字少**——右侧竖排操作栏只有图标，没有技能名称/冷却/伤害说明，玩家需要悬停或记忆。移动端触控场景下，图标按钮的可点击区域需要≥44px。
3. **右侧大片空白**——战斗界面右侧（操作栏左侧）有大片空白区域，空间利用率低。
4. **战斗日志位置**——底部战斗日志文字较小，在移动端可能难以阅读。
5. **缺乏玩家状态面板**——战斗中看不到玩家的详细属性（攻击/防御/法伤/当前Buff/Debuff），只有血条。


## 五、视觉 / UI / 立绘 / 音频分析

### 5.1 整体视觉风格

**定位**：东方写意焦墨水墨、暗黑残卷国风、低饱和度、米赭宣纸底色、无刺眼高光。

- 地图背景：水墨山水（山石、枯树、石板路、云雾），符合暗黑西游调性
- 战斗背景：水墨山水（荒山、宝塔、骷髅），有暗黑感
- 整体色调：暗金+赭石+墨黑，低饱和度，无刺眼高光

### 5.2 UI组件分析

**当前状态**：
- 按钮：基础CSS，暗金底色+金色边框，hover效果简单
- 面板：半透明黑色背景+金色边框，圆角

- 地图节点：圆形头像+连线，节点类型标签（劫印/金劫印）

**问题**：
1. **UI组件缺乏精细质感**——按钮无按压反馈、面板无纹理/光效、进度条无动画，整体感觉"能用但不够精致"。对标商业肉鸽游戏（杀戮尖塔的卡牌质感、万世剑冢的UI细节），差距明显。

3. **移动端适配**——当前截图是桌面端（778x667视口），UI布局在移动端竖屏（9:16）下是否需要重排？战斗界面的右侧操作栏在竖屏下可能需要改为底部横排。
4. **信息层级**——底部属性面板（攻/愿/善/恶/装备栏/法宝栏/宠物栏/印）信息密度高，但视觉层级不清晰，玩家可能难以快速找到关键信息。

5. **立绘动作缺失**——所有立绘都是静态的，没有攻击/受击/死亡的动作变体，这也是打击感弱的原因之一。

### 5.4 字体分析

**已放置字体**（用户确认）：
- 文津宋体（正文/UI首选，SIL OFL免费商用）
- 思源宋体（正文备选，7字重）
- 汇迹正楷（标题/匾额/碑文，SIL OFL）
- 站酷高端黑（点缀，站酷免费商用）

**问题**：
1. **字体加载确认**——字体文件已放置在img目录，但CSS中是否正确定义了@font-face并应用到对应元素？需要检查css/style.css中的字体定义。
2. **字体子集化**——中文字体文件通常较大（5-15MB），全部字集会严重影响首屏加载。需要做字体子集化（只保留游戏中用到的字符），或使用font-display: swap优化。
3. **微信小游戏首包限制**——微信首包≤4MB，字体文件如果打入首包会超限，需要CDN加载或分包。

### 5.5 音频分析

**资源**：assets/sound/ 8个音频文件（含raw子目录8个），ndx_audio_engine.js（1012行）音频引擎已建。

**重大问题**：
1. **音频几乎完全缺失**——仅8个音频文件，无BGM（地图/战斗/Boss/事件等场景音乐）、无音效（攻击/受击/技能/UI点击/获得物品）、无环境音（风声/雨声/寺庙钟声）。
2. **音频引擎已建但无内容**——ndx_audio_engine.js 1012行，说明音频播放框架已搭建，但没有足够的音频素材填充。
3. **对体验的影响**——音频是游戏沉浸感的核心维度之一。无BGM意味着地图/战斗氛围无法通过音乐营造；无音效意味着攻击/受击/UI操作缺乏听觉反馈，进一步加剧"打击感弱"的问题。
4. **对标**——杀戮尖塔有完整的BGM（每层地图不同音乐）+ 丰富音效（攻击/卡牌/遗物/UI）；万世剑冢有国风BGM + 战斗音效。本游戏在音频维度的完成度接近0%。

**改善建议**：
- P1：至少补充核心音效（攻击命中/受击/UI点击/获得物品/战斗胜利），用免费商用音效素材
- P2：补充BGM（地图探索音乐、战斗音乐、Boss战音乐、长安大本营音乐），可用AI音乐生成或免费商用音乐库
- P3：补充环境音和语音（关键剧情角色配音）

## 六、系统耦合性与肉鸽核心分析

### 6.1 系统全景图

本游戏的核心系统可分为以下层次：

```
[输入层] 英雄选择 -> 六道抉择 -> 节点选择
    |
[构筑层] 劫印(词条) + 经文(数量加成) + 装备(槽位) + 法宝(主动) + 转职(被动)
    |
[战斗层] 攻/经/绝 + 法宝 + 爆发 + 敌人AI + 意图预告
    |
[压力层] 寿数(时间) + 心魔(恶道代价) + 地区配额(万世剑冢模式)
    |
[元游戏层] 多周目继承 + 成就 + 朝代递进 + 衣冠冢/舍利塔
```

### 6.2 系统间耦合关系

| 系统A | 系统B | 耦合方式 | 评价 |
|---|---|---|---|
| 六道抉择 | 劫印 | 抉择道途决定劫印道途标签 | 核心耦合，正确 |
| 六道抉择 | 经文 | 渡道/逆道抉择获得对应经文 | 核心耦合，正确 |
| 六道抉择 | 心魔 | 恶道抉择增加心魔 | 代价耦合，正确 |
| 六道抉择 | 地区配额 | 不同道途有不同配额 | 新落地，待验证 |
| 劫印 | 装备 | 同道途劫印+同流派装备形成BD | 构筑耦合，正确 |
| 经文 | 属性 | 经文数量阈值提供属性加成 | 积累耦合，正确 |
| 寿数 | 节点选择 | 不同节点耗寿不同，影响路线 | 压力耦合，正确 |
| 心魔 | 战斗 | 心魔满100触发镜像战 | 惩罚耦合，正确 |

### 6.3 肉鸽核心评估

**肉鸽三要素**：随机性（每局不同）、构筑性（BD搭配）、死亡激励（多周目进步）。

**随机性**：
- 地图节点随机生成（杀戮尖塔式拓扑路径）——已实现
- 装备/劫印/经文掉落随机——已实现
- 事件随机——已实现（143事件池）
- 敌人组合随机——动态生成，已实现
- 评价：随机性维度完整，但81难仅22难有专属剧情，中后段的随机内容可能模板化。

**构筑性**：
- 六道（6种道途）——已实现，但区分度不足
- 劫印（47词条，有限生效格）——已实现，核心构筑维度
- 经文（数量阈值加成）——已实现，但数据量待确认
- 装备（301件，8槽位）——已实现，内容充足
- 法宝（9件，主动技能）——已实现，但数量严重不足
- 转职（64条，被动加成）——已实现
- 评价：构筑维度多（6个系统），但法宝数量不足限制了主动技能多样性，六道区分度不足限制了流派差异。

**死亡激励**：
- 衣冠冢（战斗失败，选1件装备）——已设计，待确认实装
- 舍利塔（寿尽滞留，选1装备+1套经文）——已设计，待确认实装
- 长安继承（回长安，开局带1装备+1劫印）——已设计，待确认实装
- 成就解锁（英雄/难度/内容）——已实现（38成就）
- 朝代递进（夏->商->...）——已实现2个，中后段缺失
- 评价：死亡激励的设计层次丰富（三档继承），但实际实装状态待确认，朝代系统仅2个。

### 6.4 核心问题：六道区分度

用户已明确指出"六道没有实质性区分"，这是肉鸽核心的最大隐患。

**当前状态**：
- 六道通过抉择积累点数，影响属性加成
- 但"选贪就是想多刷怪，结果实现不了，不能多拿装备"——说明六道的玩法差异未落地
- 正在落地"地区配额制"（万世剑冢模式：不同道途有不同配额，必须满足才能刷Boss）

**改善方向**（已在实施）：
- 战道：配额偏战斗（必须杀X小怪+Y精英），掉落装备多
- 渡道：配额偏事件/诵经（必须经历X事件+Y篝火），经文多、法伤高
- 隐道：配额偏隐秘（偷袭/闪避），闪避高、暴击高
- 夺道：配额偏掠夺（多刷怪/多拿资源），装备多但心魔高
- 缘道：配额偏NPC/事件（特殊NPC互动），事件收益高、隐藏内容多
- 逆道：配额偏逆经/反常规（逆道经文），独特机制、高风险高回报

**关键验证点**：配额制实施后，玩家是否能明显感受到"我选战道就是在多打架、多拿装备"，而不是"选什么都一样"。

- TapTap买断（单机肉鸽）——核心玩家市场，付费意愿强，但对品质要求高
- 浏览器H5——长尾市场，可作为Demo/试玩版

**市场机会**：
1. 西游题材+肉鸽品类的组合在微信小游戏市场有空白（当前西游游戏多为MMO/卡牌，肉鸽较少）
2. 纯H5实现，三端同步上线，边际成本低
3. 独立游戏开发者的"一人之作"故事，在TapTap有情感共鸣

**市场风险**：
1. 微信小游戏肉鸽品类留存率普遍偏低（首周留存<20%），需要强社交/分享机制
2. TapTap买断制肉鸽游戏竞争激烈（杀戮尖塔移动端、哈迪斯、传说法师等），品质门槛高

4. 音频/打击感不足会严重影响口碑，TapTap玩家对品质要求高

**上线建议**：
1. 先上线微信小游戏（免费+广告），验证核心循环和留存，收集数据
2. 打磨品质（打击感+音频+内容填充）后，上线TapTap买断版
3. 浏览器H5作为Demo/试玩版，用于获客和口碑传播
