00 / SUMMARY

结论摘要一页读完的判断

这是一款内容体量远超同类独立作品、系统骨架完整、但"完成度"与"打磨度"严重错位的作品。代码层面它已经是一个可交付的成品（51,626 行、33 项门禁全绿、三端抽象齐全）；体验层面它仍处在"装配完成但未调校"的状态——多处资源层硬伤与表现层工程债会在玩家进入前 10 分钟就暴露。

◆ 已经站得住的部分
  • 内容体量扎实：301 件装备、199 片经文残篇、143 个随机事件、60 件法宝、81 难 × 17 区域、5 英雄 × 15 个绝招。这个量级在独立 H5 Roguelike 里属于上游。
  • 系统耦合有设计：六道计数 → 解锁攻击风格（game_core_3.js:85-87）、法宝 cleanse 克制 Boss debuff、经文渡/逆双线，都不是单纯堆数值。
  • 工程纪律罕见地好：33 项门禁、真源解析型 loader、模块化拆分（ui 16 shard / game 23 shard），说明长期可维护性被认真对待。
  • 战斗反馈链路完整：hit-stop、意图预告、连招、气势层级、飘字三档分级均已落地，不是空壳。
◆ 会立刻劝退的部分
  • 16 个关键角色立绘 404：哪吒、二郎真君、如来、观音、接引使者（新手指引角色）——引用 .png，实际文件是 .webp。
  • 5 首 BGM 全部 30.0 秒：单局 30–45 分钟，同一段旋律每分钟循环两次。
  • 资源 104MB / 829 文件：无懒加载、无预加载，单张 6.6MB PNG 且已存在 webp 副本却仍在用 PNG。
  • 107 个脚本串行加载：无打包、无 defer，首屏白屏风险随网络波动放大。
一句话建议 在继续"加内容"之前，先做一轮为期 3–5 天的资源与表现层收口（P0 三项 + P1 前四项）。这些内容不增加任何新玩法，但决定玩家会不会留到第 10 分钟。当前最大的风险不是"内容不够"，而是"已有内容没被正确显示出来"。
01 / METHOD

审计方法与证据基准为什么可以信这份报告

本报告遵循项目既有宪法：代码为最终真源，文档不作为依据。具体做法是——

  • 规模计数：不数字符串，而是用与 regression.js 相同的宿主环境真实加载逻辑层（按 index.html 解析加载序，排除 DOM-only 的 ui/main/sound），在运行时枚举 NDX 上的数组与对象条目数。
  • 数值实测：战斗回合数、BGM 时长均通过脚本实跑/帧解析得出，不引用历史文档结论。
  • 资源校验：立绘引用逐条做文件系统存在性检查；音频做 MPEG 帧头解析取真实时长与码率。
  • 凡冲突处以代码为准：发现与历史文档/记忆不符的数值，一律在附录列出失真清单。
方法局限（如实标注） ① 战斗模拟采用"裸模型"玩家（线性缩放基础攻防，不含装备/经文/法宝乘区），因此绝对数值仅供量级与趋势判断，不代表真实配装下的体验；② 视觉与手感类结论需浏览器目测复核，静态审计只能证明"逻辑正确"不能证明"观感正确"；③ 工作树存在大量未提交改动，本报告基于当前磁盘状态。

03 / DESIGN

游戏设计完整度核心循环是否成立

3.1 核心循环拆解

《逆道西行》的单局循环是标准的 StS 式地图推进：选节点 → 结算（战斗/事件/商店/营地/淬炼）→ 获得资源（装备/经文/法宝/道途点）→ 强化 build → 下一节点，17 个区域 × 81 难构成单局长线，跨周目通过存档/轮回继承。

循环各环的设计完整度
环节实现状态决策密度评价
节点选择完整中81 难节点树 + 节点类型分布，玩家有路线取舍
战斗完整中偏低三键 + 连招 + 气势，但战斗时长被数值锁死，build 强度不转化为时长缩短（见 §5.4）
事件完整中143 条、选项带六道 fate，有风险收益；但分布不均（见 §4.6）
构筑（build）偏弱低装备 301 件但 280 件无 rarity 字段，品质分层靠 chapter；词条维度少（atk/matk/hp/dr）
长线（跨周目）完整中存档 + 轮回 + 镜鉴 + 藏珍阁，6 个结局
元进程薄低成就 38 条为被动记录，无解锁型元奖励闭环

3.2 最突出的设计结构性问题

问题 A · 构筑深度与内容体量不匹配 301 件装备是一个很大的数字，但装备的数据结构是 {id,name,slot,atk,matk,hp,dr,desc,set,setTier,chapter,sys}——只有 4 个数值维度，没有词条/词缀/随机属性。这意味着装备是"可枚举的最优解"而非"可组合的构筑空间"：玩家很快会学会"挑 atk 最高的穿"，而不是"围绕某个机制搭一套"。

改善方向：不一定要加随机词条（会破坏可控性）。更具性价比的是强化套装与共鸣的表达力——目前 SET_DAO 24 组 / SET_RESONANCE 24 组 / CROSS_RESONANCE 16 组已经是现成的骨架，把"共鸣触发条件"从静态数值改为可感知的战斗事件（如"连续 3 次破韧触发 X"），就能用既有数据结构撑起构筑深度。
问题 B · 战斗时长被数值曲线锁死，玩家成长无法被"感受到" 实测（§5.4）显示：在难 20，玩家攻击从 0.6× 提升到 2.5×，战斗回合数从 9 → 7，几乎不变；血量翻倍反而让战斗变长（9 → 18 回合）。根因是怪物 HP 随难度指数增长（monsterAt 采用 (d/20)^1.16 缓坡曲线），玩家与怪物同步膨胀，净结果是"数字变大了但打起来一样久"。

这是 Roguelike 的大忌：玩家投入 30 分钟做 build，最直接的反馈应该是"我现在砍得更快了"。当前设计把这个反馈吃掉了。
问题 C · 前期节奏与耐心预算的错配 FIGHT_GATE = { auto:4, speed2:3, speed3:10, skip:15 }——前 3 个地区强制手动、无倍速，第 4 地区才开自动。这个设计的初衷是"让玩家先学会三键"，但对于会重复游玩的 Roguelike，第二周目起这就是纯粹的时间税。

建议：把强制手动期与"是否首次游玩"绑定（存档标记），而非与地区号绑定。首周目保留教学，二周目起直接开放。

评价：这是全项目设计得最好的系统。渡/逆双线不只是数值正负，而是绑定了六道归属（SUTRA_DAO_OF）、区域分布（SUTRA_REGION）与专属事件（SUTRA_EVENTS 154 条），意味着"选渡还是选逆"会真的改变后续能遇到什么。199 片残篇提供了充足的收集纵深。

4.2 道途 / 六道系统 完成度高

六道计数直接驱动战斗能力解锁——这是全项目最优雅的一处耦合：game_core_3.js:85-87 中，六道计数 ≥3 时解锁对应攻击风格（战→combo、夺→burst、逆→pierce）。玩家在事件中选的六道选项，直接转化为战斗中的操作空间。

配套数据：SET_DAO 24、SET_RESONANCE 24、CROSS_RESONANCE 16、SUTRA_DAO_TAG 27。

P1 反馈延迟过长：风格解锁发生在"计数达到 3"的瞬间，但玩家要等到下一场战斗才能感受到。建议在解锁时给一次明确的即时反馈（弹窗 + 战斗内首次自动演示该风格）。

评价：装备是"内容量最大但设计最保守"的系统。301 件的体量配 4 个数值维度，结果是信息过载而选择贫乏——玩家面对大量装备，决策却退化成"比大小"。

改善建议（按性价比排序）：

  • ① 补 rarity 字段（280 件）——纯数据补全，零玩法风险，立刻让装备有品质层级与掉落期待感。
  • ② 给装备加"机制标签"而非随机词条——例如 onBreak（破韧时触发）、onLowHp（残血触发）。可在不改数值体系的前提下，让装备从"比大小"变成"搭机制"。
  • ③ 收窄 CRAFT_POOL（187 → 100 左右）——锻造池过大会让定向构筑失去意义。

4.4 法宝系统 完成度高

60 件法宝，含英雄专属成长链（ch1→ch4 随章节自动进阶，enterNode 每节点调用 upgradeHeroTreasure）与 cleanse 克制机制（TREASURES[id].effect.cleanse 解 Boss debuff）。这两处都是 V8.5x 才补完的，说明团队在持续加深度。

P2 60 件法宝相对 301 件装备存在感偏弱。法宝作为"免费动作"本应是战斗中的战术支点（StS 的药水/遗物定位），建议检查：单局平均能获得几件？如果 < 5，玩家很难形成"围绕法宝打"的意识。

4.5 宠物系统 规模待确认

立绘目录 img/portraits/pets 仅 5 个文件，映射表未进入 Top 20。从资源侧推断宠物规模较小（约 5 种），与"宠物独立机制"的设计定位相比偏单薄。建议确认是否为有意克制，还是需要补内容。

4.6 事件系统 体量好 · 分布需查

143 条事件，结构为 {title, text, opts[]}，选项带 fate（六道归属）、fight、reward、effect。事件文本质量很高（样例："荒碑半埋，碑文是一部没写完的西游——写到'五行山'三字便断了，像是写的人自己也没走出去。"）——这是项目的强项，黑暗西游的调性在文案层面立住了。

P1 本次审计中，143 条事件均未检出 act 字段（此前审计曾按 act 统计分布并修补过 act2/act15 密度）。需确认分布字段已改名（如 region/chapter）还是字段丢失——若为后者，事件可能未按区域正确投放。

4.7 地图 / 试炼 / 81 难 完成度高

17 区域（ACT_NAMES / ACT_BG / ACT_MAP_THEME 各 17）× 81 难（TRIAL_BOSS 81、TRIAL_LIB 81、REGION_QUOTA 17）。区域名已全部落地为真实地名（大唐境内 / 两界山 / 黄风岭 / 流沙河 / 五庄观 / 火云洞 / 车迟国 / 通天河 / 女儿国 / 真假猴王 / 火焰山 …），17 个 Boss 名也已完成（刘洪·江流索命 → 通天河老鼋·湿经）。主线叙事骨架完整。

P2 img/portraits/bosses 有 31 个文件，而 Boss 只有 17 个——存在富余版本或未接入的立绘（详见 §6.3）。

4.8 经济与资源循环 需实机验证

商店 / 营地 / 淬炼 / 论道等模块齐备（game_shop / game_camp / game_rest / game_compound），COMMON_MATS 13 种材料、RECIPES 207 条配方。结构完整，但经济平衡（金币产出/消耗曲线、是否出现死货币）需实机多局采样才能判断，静态审计无法下结论。

4.9 存档与跨周目 完整

SaveSystem（18 方法）+ 藏珍阁（game_vault）+ 镜鉴（data_mirror 417 行）+ 轮回（data_reincarnation 335 行）+ 6 个结局。跨周目继承链路明确。regression 已覆盖存档 round-trip 断言。

4.10 成就与埋点 被动

成就 38 条（ACHIEVEMENTS + ACH_BY_ID），埋点 telemetry.js 采用 CAP=200 环形缓冲。两者目前都是"记录型"而非"驱动型"——成就不解锁内容，埋点未回流到设计迭代。建议：至少让成就解锁少量元奖励（如开局小加成），把被动记录变成主动目标。

P1 诵经定位模糊：5 个诵经全部是"法伤 + 附加效果"（回血/激昂/吸血/护盾/匿踪），没有一个提供减伤或防御姿态。这导致三键实际上是"两个攻击键 + 一个大招"，缺少 StS 式"防御"这一极。建议把其中一个英雄的诵经重定义为守势姿态（减伤 + 反击），让三键形成真正的攻 / 守 / 爆发三角。

已有的令牌定义本身是专业的——:root 里定义了完整的"暗墨·佛光"调色板（玄墨/赭石/骨白/朱砂/鎏金/翠绿/青金石/暗紫/旧铜）与四档字体规范（display/title/body/num/mono），设计判断是对的。问题在于定义了但没用起来：23 个变量对抗 4,165 处硬编码色值。

字体同理：@font-face 正确声明了 4 个子集字体（汇迹正楷 + 文源宋体 Regular/Bold/Heavy，font-display:swap），但 font-family 实际使用中，直接写系统楷体（STKaiti/KaiTi）82 处，使用令牌仅 26 处。后果是：在 iOS / 微信小游戏等无楷体的环境会回退到默认字体，自研字体的视觉投入被浪费。

这是表现层最值得做的一件事 把硬编码色值与字体批量替换为令牌。不需要重写任何视觉，纯机械替换 + 逐屏目测。收益：① 主题色可一处修改；② 自研字体在所有端真正生效；③ 后续任何视觉调整成本下降一个数量级。建议用脚本批量替换 + 三端目测回归。

6.4 动效

251 个 @keyframes，覆盖骨架屏、弹窗淡入、点击反馈等。项目有一条明确铁律：位移演出禁用 CSS @keyframes（因为每回合 doRender() 会重建 .fb-arena，导致动画每帧从 0% 重播），位移一律走 JS 时间驱动 + !important 内联 transform。这条铁律是对的，且已被遵守——hit-stop 与冲撞都通过 JS 时间驱动实现。
