### 1.2 四个源的真实状态 —— 「四源优先级」是伪问题

| 源 | 落地函数 | 生产调用点 | 状态 |
|---|---|---|---|
| ① **经文（经位经书）** | `sutraVariantOf` + `applySutraVariant` | 3 处 | ✅ 生效 |
| ② **职业（隐藏职流派）** | `applyJobStyle` | `combat_active.js:73 / 218 / 309 / 333` | ✅ 生效 |
| ③ **法宝** | `applyTreasureStatus`（在 `finalizeActiveAct` 内） | 非大招键 | ✅ 生效 |
| ④ **技能变种表** `ATK_VARIANTS` / `CHANT_VARIANTS` | `applyActVariant` | 🔴 **零** | 🔴 **死数据** |

🔴 **结论**：路线图写的「变体四源谁覆盖谁」，其中**第四个源（技能变种表）从未接线**。
`NDX.ATK_VARIANTS`(10 个普攻变种) 与 `NDX.CHANT_VARIANTS`(10 个诵经变种) 全程只被门禁脚本 `_verify_skill_variant.js` 调用，战斗里一个都没生效过。

> 这是本轮最重要的发现：**不是优先级没定，是有一源根本不存在于运行时。**
> 在此之前讨论「谁覆盖谁」没有意义 —— 覆盖关系的另一端缺了一整张表。

### 1.3 实锤 bug：同一变体被应用两次

| 键 | 直接调 `_sutraVariant` | `finalizeActiveAct` 内调 | 重复 |
|---|---|---|---|
| 攻 | `:75` | `:79`（内部 `sutraVariantOf`+`applySutraVariant`） | 🔴 **2 次** |
| 绝招 | `:305` / `:331` | `:307` / `:332`（`kind==='ult'` 分支仍读 `slots.atk`） | 🔴 **2 次** |
| 诵经 | — | `:222` | ✅ 1 次 |

`applySutraVariant`（`combat_active.js:530-545`）里加法类字段会被**叠加两遍**：

- `healPct` / `lifestealPct` / `shieldPct` / `trueDmgPct` / `dotPct` → **数值翻倍**
- `dmgMul`（如《法华经》mult 1.5）→ 1.5 倍算完再一次 → 实际 **×2.25**
- `note` → 字符串拼接两次，**战斗日志出现两遍同一条经文名**

影响范围：所有持攻击格经文/已合成逆经打普攻与绝招的玩家。诵经键不受影响。

### 1.4 遗留口径问题

`finalizeActiveAct`（`data_skill_variant.js:543-544`）注释自称「种类变种 + 法宝状态 + 大招职业变体」，
但 `ATK_VARIANTS` 段（`:107-109`）标着 V9.29「普攻变种」——两张表都自认是"种类变种"。
**谁替代谁、是否废弃，代码里没有交代**，是长期悬而未决的口径冲突。

## 二、目标框定（S1 · `game-design-goal-framing`）

### Goal statement

> 让**技能层成为三键玩法的可辨识载体**：玩家每次按攻/诵/绝三键，都要能说出"这一下为什么和昨天不一样"，
> 且这种"不一样"由**可见的四个来源**（经文 / 职业 / 法宝 / 英雄）叠加构成 —— 以修复「技能变种表零生效」与「变体重复应用」为起点，
> 在 **A3 批次内（一个系统，不改战斗内核）** 使：持任一经文 + 任一隐藏职业的组合，三键手感**确定不同且日志可核对**。

### Purpose（为什么存在）

| 问题 | 现在 | 目标 |
|---|---|---|
| 换经有没有手感 | 有，但**翻倍了**（bug） | 有，且数值与描述一致 |
| 转职有没有手感 | 有（`applyJobStyle` 三键全接） | 保留，且不与经文争夺同一字段 |
| 技能层自己有没有内容 | 🔴 无（变种表零生效） | 有，作为第四个可感知维度 |
| 玩家能不能复盘 | 日志出现重复经文名 | 每条改动在日志里**只出现一次** |

**玩家行为应改变**：从「我换了个经，伤害数字变了（但可能不对）」→ 「我换了**流派**，三键的**行为**变了（打法变了，不是数字变了）」。

### Fit with the Game

- **上游已通**：六道(L0) ✅、职业(L1) ✅、经文(L2) ✅（V9.54 双格已落地）。技能层是这三者**价值的放大器**——职业与经文做得再好，若三键不出手感，玩家感知不到 = 白做。
- **不与 L4 冲突**：本系统只碰 `act` 的生产与后处理，**不碰结算**（`combat_part1.js` 预结算 + 回放架构不动）。
- **必须守住的单源纪律**：技能变种表的数值**只此一处**，禁止外围文件再持倍率（`data_skill_index.js` 已立的收口规则）。
- **不能稀释的**：英雄本命三键（`applyHeroKeyFeel`）是身份识别，变体层只能在**其上叠加**，不得覆盖 `act.kind` / `act.name`。

### Success criteria（可验收）

| # | 判据 | 如何测 |
|---|---|---|
| S1 | `applyActVariant` 有**生产调用点** | grep 排除 `scripts/` 后非空 |
| S2 | 任一经文 + 任一隐藏职组合，三键 act **与默认组合差异可枚举** | 门禁遍历组合快照 |
| S3 | 同一变体**只应用一次** | 断言 `note` 不重复 + 数值等于单倍口径 |
| S4 | 战斗日志每条来源只出现一次 | 采样战斗日志去重断言 |
| S5 | 外围 7 文件零倍率常量 | 沿用 `data_skill_index.js` 既有规则，加门禁 |

### Constraints

- **范围**：只做 `data_skill_variant.js` + `combat_active.js` 的变体层，**不动战斗内核、不动属性、不动 UI 布局**。
- **不引入第二真源**：数值全部落在这两个文件，其他系统不得复制。
- **存量玩家零副作用**：未持经、未转职、未装法宝的玩家，三键 act **逐字节不变**（与 A1 流派模型同一条保证）。
- **时序**：必须**先定优先级再改码**。反复改接口是 A1 批次的教训。

> 没有任何地方声明「谁先谁后」，调顺序只能改代码。这正是「变体重复应用」能藏这么久的原因。

# 四、方案（S2 · 拆方案）

## 4.1 总表架构：三层收口

```
js/data_skill_index.js  ← 【技能数据总表】唯一真源
│
├─ 层一 元信息      NDX.SKILL_CLASSES          （既有，保留）
├─ 层二 数值真源    NDX.STATUS_DEFS            （从 data_skill_variant.js 迁入）
│                   NDX.TREASURE_STATUS        （迁入）
│                   NDX.ATK_VARIANTS           （迁入 + 参数化）
│                   NDX.CHANT_VARIANTS         （迁入 + 参数化）
│                   NDX.ULT_STYLE_MOD          （迁入）
│                   NDX.JOB_STYLE_VARIANT      （新增：流派 → 变种映射）
└─ 层三 统一调配    NDX.SKILL_ORDER            （新增：执行顺序真源）
                    NDX.resolveSkillAct(act, kind, ctx)  （新增：唯一出口）
                    NDX.applyActVariant(...)   （保留，改走总表数值）
```

```js
// 执行顺序真源：唯一声明处，改顺序只改这里
NDX.SKILL_ORDER = ['hero', 'dao', 'job', 'variant', 'sutra', 'treasure'];
```

`combat_active.js` 的三键分支**不再自己编排顺序**，只调 `NDX.resolveSkillAct`。
这是「统一调配」的落地形态：**顺序可被门禁校验、可被单点调整，不再散落在 8 段语句里**。

## 4.2 加载顺序调整（硬约束）

现状：`index.html:254` `data_skill_variant.js` **早于** `:280` `data_skill_index.js`。
总表接管数值后必须反过来：

| 文件 | 动作 |
|---|---|
| `index.html` | `data_skill_index.js` 移置 `data_skill_variant.js` **之前**（建议插在 `:253` 后） |

兼容做法：**沿用原 `NDX.STATUS_DEFS` / `NDX.ATK_VARIANTS` 等字段名**，
`data_skill_variant.js` **不再声明**，仅保留执行函数（状态落地 / 减伤传播 / 反击落地 / 编队同步）。
生产侧对本表系的唯一读取是 `combat_active.js:446`（`STATUS_DEFS.ward.drUp`），迁移零回归。

## 4.3 变种从哪来（Q1-A 的隐藏前提）

⚠ **接线前的必答题**：`applyActVariant` 需要知道「此刻该用哪个变种」。
现状**没有任何 UI 让玩家选变种** —— 若无来源，接线等于固定一个变种，玩家感知不到。

**结论：变种 = 隐藏职流派的表现层**，由 `JOB_STYLE` 派生，不新增 UI：

```
JOB_STYLE[jobKey] → 'combo'|'crit'|... → NDX.JOB_STYLE_VARIANT[style] → 变种 key
未转职 / 未落地流派 → 'plain'（直击）
```

| 理由 | 说明 |
|---|---|
| 零新 UI | 符合 S1 约束「不动 UI 布局」 |
| 零副作用 | 未转职玩家 → `plain` → 行为逐字节不变 |
| 可感知 | 玩家转职瞬间三键**打法形态**变了（不是数字变了），正是 S1 Purpose 要的 |
| 零新数值 | 10 个流派直接复用既有 10+10 张变种表，不造新数值 |

## 4.4 接线位置与去重（Q2-A）

**去重**：删 `combat_active.js:75` / `:305` / `:331` 三处 `_sutraVariant(act, ...)` 直调，
经文变体交回 `finalizeActiveAct`（`:567-570` 已有该分支），攻键只留一处。

**变种插入位置**（🔸 技术必然性，非设计取舍）：

```
... 经文变体 → 【技能变种】→ 法宝状态
```

理由：`sac-shield`（舍攻为盾）语义是「放弃本次攻击」，它必须**在经文加成之后**执行，
否则经文的 `dmgMul`（如法华 1.5）作用在已被归零的 `dmg` 上，整层经文收益被吞掉。
放在最后才能保证「弃攻」是真的弃掉加成后的那一击。

## 4.5 兼容与回滚

| 保险 | 说明 |
|---|---|
| 字段名不变 | 总表沿用 `NDX.ATK_VARIANTS` 等原名，不改名、不换文件引用 |
| 未转职零变化 | `plain` 分支 `apply: null`，`act` 逐字节不变 |
| 单测可回滚 | 全部改动集中在 3 文件 + `index.html` 一行顺序，回退成本 ≤ 1 次 `git revert` |
| 无存档迁移 | 全部为运行时派生，不读存档 |

# 五、数值表（S4 · `game-numeric-design`）

> ⚠ **所有数值原样继承，不重做平衡** —— 它们此前从未生效，接线即「新增内容」而非「改数值」。
> 下表只做**参数化**（从 `apply` 函数里抽成字段）与**定位标注**，便于门禁比对与后续调参。

## 5.1 攻键变种 `ATK_VARIANTS`（迁总表 · 参数化）

| key | 名称 | 操作 | 参数 | 定位 | 接线后影响 |
|---|---|---|---|---|---|
| `plain` | 直击 | — | — | 基线 | 无（未转职者恒此） |
| `sac-shield` | 舍攻为盾 | shield | `shieldPct` 0.9（dmg→0） | 攻守转换 | 放弃本次伤害，换 90% 护盾 |
| `drain` | 噬血 | heal | `healPct` 0.22 | 续航 | 吸 22% 伤害值 |
| `combo` | 连环 | multi | `hits` 2 / `spread` 0.35 | 小连击 | 2 段，总伤持平（每段 70%） |
| `crit` | 战意 | crit | `critDmgAdd` 0.5 | 爆发 | 必暴 + 暴伤 +50% |
| `sunder` | 破相 | trueDmg | `trueDmgPct` 0.25 + armorBreak | 破防 | 25% 无视防御真伤 |
| `guard` | 御守 | guard | `dmgMul` 0.8 / `dr` 0.25 | 防守 | 伤害 −20% 换本回合减伤 25% |
| `multi` | 多重攻击 | multi | `dmgScale` 1.15 / `hits` 3 / `spread` 0.20 | 群攻 | **总伤 ×1.15**（跨回合 3 段连落） |
| `aoe` | 群伤 | aoe | `aoePct` 0.6 | 群体 | 其余目标 60% 溅射 |
| `counter` | 反击 | counter | `counterPct` 0.6 / `counterLifesteal` 0.30 | 反打 | 承伤 60% 回打 + 吸 30% |

🔴 **S5 落地时修正了本行的原数值**（原 `dmgPct` 0.42）。详见 **§7.2**「错误二」：旧值在引擎「`dmg` 是总量、按 `hits` 分摊」的口径下实为**净削弱 58%**，与 desc 写的「×1.15」完全相反。
修正后 = `dmgScale` 1.15 + `hits` 3 + `spread` 0.20，与 desc 语义一致。

## 7.2 落地抓出的两个错误

### 错误一：同一变体被应用两次（真 bug）

原 `combat_active.js` 的语句序列里，`applyActVariant` 在某些分支会被执行两次；变种表从未接线，所以一直没暴露。修法 = 逐层幂等登记 `act._skillDone[layer]`，同一层在同一 act 上永不执行两次。

### 错误二：`multi` 数值语义错误（🔴 影响较大）

S2 阶段判断「`multi` 是 20 个变种里唯一的正收益项，接线后白强 26%」，并据此建议「降至 0.38」。**S5 端到端实测推翻了这个判断。**

引擎口径（`combat_active.js:366`）：

```js
const hits = (act.spread && act.hits > 1) ? act.hits : 1;
const perHit = hits > 1 ? (act.dmg + trueDmg) / hits : (act.dmg + trueDmg);
```

⇒ **`act.dmg` 是总量、按 `hits` 分摊到连续回合**，`spread` 只判真值。

旧数据写 `dmg × 0.42 + hits 3`，等于「把总伤砍到 42% 再分 3 回合」= **净削弱 58%**，而 desc 还写着「总伤 ×1.15」—— 写的与算的完全是两回事。变种表从未接线，错误因此从未暴露。

**修正**：按 desc 的真实语义落地 = `dmg` 是总量 ⇒ 直接 ×1.15，再拆 3 击跨回合连落。

```js
multi: { name: '多重攻击', desc: '三段连击（总伤 ×1.15，跨回合连续落下）',
         fx: [{ op:'dmgScale', v:1.15 }, { op:'hits', v:3 }, { op:'spread', v:0.20 }] }
```

⚠ **连带作废 S2 阶段的一条结论**：「`multi` 白强 26%」是误算（按「每段全额」口径算的）。**用户本轮拍板的「multi 降至 0.38」因此方向反了** —— 已按修正后的语义落地为 `dmgScale 1.15`，**此项须用户追认**（见 §八）。

## 7.3 方法论沉淀

- ⚠ **门禁绿了不等于做对了** —— 本轮门禁 G1~G7 首跑全过，但 `multi` 的数值错误是靠**端到端实测脚本**才抓出来的。以后每个系统落地都要写 e2e，不能停在「绿了」。
- ⚠ **参数化时 data 的语义必须与引擎消费口径对齐** —— 本轮 `multi` 的 0.42 在「总量分摊」口径下是削弱、在「每段全额」口径下才是增强。不读引擎就抽参数，只会把错误从函数搬到数据。
- ⚠ **架构迁移会让源码文本级断言变红** —— 判红前先分清「真回归」vs「断言指向了旧位置」。
