劫印来源真源收口 —— 死模块 data_seal_source.js 的处置

《逆道西行》· 落地报告 · 2026-09-12 · 承接「六道 = 概率主干」四池偏置（§2.2/2.3）与「六道零属性」（§2.1），本轮收掉挂账最久的一项：281 行零调用的劫印来源模块

一句话结论：js/data_seal_source.js（281 行、全仓零调用）的三条核心前提与项目真实结构直接冲突，不能按原样接线——但它记录的「来源 → 品质档位」设计意图在真源里是散落硬编码的。本轮把它降级为真源表并入劫印 owner，收敛 5 文件 6 处判定，并把唯一有价值的「主道契合度」变成玩家可见的 UI 标签；逐位等价、零回归。

一、判定：为什么它不能按原样接线

依「代码为真源」逐条核对，该模块的三个核心假设全部不成立：

模块假设项目真实结构结论
rollSource()：按权重表随机决定本次劫印从哪来（战斗 60% / 精英 10% / Boss 5% / 事件 10% / 商店 8% / 许愿 5% / 精炼 2%） 来源由节点类型决定——打了劫难就战后给、精英战就给蓝劫、融合节点结算就给、非战斗劫难就给善印。不存在「玩家没做事却随机掉一个来源」 机制冲突
rollQuality()：按来源的概率权重抽品质（如 Boss 白10/蓝30/金50/红10） 品质由公式直给：Boss 必金、精英固定蓝、普通劫难白为底 + 按章提升蓝率。不是抽取 机制冲突
品质含 red（红劫），四档 NDX.SEAL_WORDS[*].tiers 仅 white / blue / gold 三档（UI 词表预留了「红劫」但数据层从未有值） 数据不存在
道途键为英文 du / zhan / yin / duo / yuan / ni；字段 seal.quality / seal.type / seal.value 全项目已统一中文六道（战/渡/缘/夺/隐/逆）；劫印字段为 seal.tier / seal.stat / seal.val 口径不符

也就是说：它不只是「没接线」，而是接了也会错（英文道途键在中文六道体系里永远匹配不上）。这解释了它为何躺在 index.html 加载了却全仓零调用。

但它并非一无价值

真实代码里的品质档位判定是散落在 5 个文件 6 处的硬编码：

来源原实现位置原口径
普通劫难 / 关隘 Bossgame_combat_2.js:312Boss 金；否之白为底 + 0.04+0.02×章 蓝率（上限 0.5）+ 逆道抉择每次 +20%（上限 60%）

这正是 data_seal_source.js 想统一表达、却因前提错误而没做成的事。正确处置 = 把它降级成一张正确的真源表，然后让散落处来消费它。

二、处置：数据归位（一删 / 一立 / 六收 / 一显）

#动作内容
①删 删除 js/data_seal_source.js（281 行）及 index.html 加载行——前提冲突的死代码
②立 真源并入劫印 owner js/jieseals.js：
· NDX.SEAL_SOURCE_TIER —— 5 类来源（trial/elite/fusion/good/xinmo）× 档位规则 × 阵营
· NDX.rollSealTier(source, s, opt) —— 统一档位结算（含按章蓝率、逆道进阶、Boss 必金、融合档位）
· NDX.SEAL_SOURCE_ALIGN —— 阵营 → 道途池（evil 战/夺/逆 · good 渡/隐/缘）
③收 5 文件 6 处判定全部改走 NDX.rollSealTier(…)；offerSealsAligned 的内联 GOD/EVIL 改读 NDX.SEAL_SOURCE_ALIGN（第二份池定义消除）
④显 把死模块里唯一未落地的有效能力——主道契合度——按真实中文六道重写（NDX.SEAL_DAO_RELATED / sealDaoAlignment / sealAlignmentLabel），在劫印三选一卡片上显示「主道契合 / 相关道」标签

关键设计点

  • 不引入并行体系（宪法 §五）：真源落在劫印 owner jieseals.js，而不是新起一个模块；调用的仍是最初的 offerSeals / offerSealsAligned，只把「tier 从哪来」换成了真源。
  • 逐位等价而非「大概一致」：rollSealTier 内 Math.random() 的顺序与次数严格镜像旧代码——Boss / 固定档位 / 融合三条路径不掷骰；白为底时先掷「按章蓝率」，仅在仍为白且逆道抉择 > 0 时才掷「逆道进阶」（保留短路）。
  • 相关道关系统一对称：沿用原设计的「战↔夺↔逆」「渡↔缘↔隐」三三成组，每道恰 2 条相关道 → 主道外均匀三分（1 主道 / 2 相关 / 3 跨界）。
  • UI 只做加法：跨界不发标签（避免噪音），只提示「主道契合 / 相关道」两类有决策价值的信息。

三、逐位等价：证据而非声明

门禁 A 组用内联的迁移前原式作参照实现，对同一随机序列分别跑「旧式」与「真源」，比对结果 + 掷骰次数双指标：

  • 用例矩阵：act 1..9 × isBoss true/false × sealUp 0/1/3/5 × 4 组随机种子 = 288 组
  • 另加边界：s.act 缺失（旧式产生 NaN 比较 → 恒白），真源同口径
  • 固定档位路径（精英 / 非战斗 / 心魔 / Boss / 融合）额外断言 掷骰次数 = 0——这是「没有偷偷多掷一次骰子」的硬证据

五、发现但未擅自处理

  • index.html 是 CRLF + 孤立 CR 混合换行（\n 计数 474、CR 计数 946）——字符串匹配必须逐行处理，字节级断言（count('\\n')==count('\\r\\n')）会误判。本轮因此踩了一次，已改为「按行删除 + EOL 计数守恒」。
  • UI tier 词表预留了「红劫」（ui_panel_2.js 的 red:'红劫'）但数据层 SEAL_WORDS.tiers 只有三档——是"预留"还是"遗漏"，需你拍板是否补第四档。
  • 转职 daoGate：§2.1 要求取消读 fate[dao]，但 GDD §十一 Q1 自标「待决」且建议「保留作软前置」，两者矛盾——未动，待拍板。
